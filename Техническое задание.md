## 3. Главный принцип: одинаковое поведение на всех платформах

Это правило обязательно для всего проекта. Оно важнее удобства отдельной платформы.

**П1. Функция, которая не работает одинаково на Web, Android и iOS, в проект не включается.** Либо для неё есть единая реализация на всех трёх платформах, либо её нет нигде.

**П2. Разрешено:**
- стандартные виджеты Flutter и Material 3;
- пакеты, которые официально поддерживают **Web, Android и iOS одновременно**, например `http`, `shared_preferences`, `url_launcher`, `cached_network_image`, `package_info_plus`;
- выбор раскладки экрана по ширине (`LayoutBuilder`), а не по названию операционной системы.

**П3. Проверка платформы в коде** (`kIsWeb`, `defaultTargetPlatform`) разрешена только в одном файле `lib/core/platform/distribution.dart`. Там разрешено решать только, как показать способ установки:
- в браузере — кнопки магазинов и подсказку «Установить как приложение»;
- в приложении из магазина — не показывать их.

Бизнес-функции и экраны от платформы не зависят.

**П4. Запрещено (не входит в проект):**

| Возможность | Почему исключена |
|---|---|
| Push-уведомления (FCM, APNs, RuStore Push, Web Push) | На каждой платформе своя технология. В Safari на iOS работают только из установленного PWA |
| Биометрия, Face ID, отпечаток пальца | Недоступна в браузере |
| Геолокация, камера, NFC, контакты, календарь | Разное поведение и разные разрешения на платформах |
| Встроенные покупки (IAP) и платёжные SDK | Для заказа обедов не нужны. Если оплата понадобится, только через веб-страницу оплаты (решается отдельно) |
| Deep links и Universal Links | Для каждой платформы своя настройка. Восстановление пароля работает только в браузере, как в шаблоне NewProject |
| Отдельные сборки под Windows и macOS | На компьютерах используется браузер |
| Отдельные экраны в стилях Cupertino или Fluent | Запрещено шаблоном NewProject |
| Работа с данными без интернета, синхронизация | Шаблон требует постоянного подключения |
| Код, который выполняется только на одной платформе (`dart:html`, `dart:io`, платформенные каналы) в `features/` | Нарушает П1 |

**П5.** Исключение из П1–П4 возможно только через отдельную запись в `ARCHITECTURE.md` (ADR). В записи указывается причина и как функция будет работать на всех трёх платформах.

## 4. Архитектура решения

### 4.1. Сайт и приложение — одна сборка Flutter

Чтобы не делать второй проект (цель Ц3), информационные страницы сайта тоже делаются на Flutter, в той же кодовой базе.

```text
Один репозиторий Flutter
│
├── Web-сборка → obedmoscow.ru (Caddy)
│     /                  Главная (сайт)
│     /about, /delivery, /how-to-order, /contacts
│     /install           Как установить: магазины, APK, установка PWA
│     /sign-in, /sign-up, /reset-password
│     /menu, /cart, /orders, /profile   ← раздел приложения
│     + manifest.json → установка как PWA
│
├── Android → Google Play, RuStore, APK на /install
└── iOS     → App Store

Все клиенты → HTTP-сервисы 1С (без изменений) + /data/dishes.json, /data/pictures/
```

- **В браузере** открывается главная страница сайта. Кнопка «Заказать обед» ведёт в раздел приложения (`/menu`). Кнопки магазинов ведут на `/install`.
- **В приложении из магазина** сразу открывается меню. Страницы сайта доступны в разделе «О компании».

### 4.2. Первая загрузка и поисковики

У сайта на Flutter есть два известных недостатка: поисковики почти не видят текст, а первая загрузка тяжёлая (2–3 МБ). Решение без второго проекта:

- **Т-SEO-1.** Файл `web/index.html` лежит внутри Flutter-проекта. В нём заранее прописаны `title`, `description`, Open Graph, разметка `schema.org/LocalBusiness` (адрес, телефон, часы работы), а также лёгкий HTML-экран загрузки. Этот экран показывает название, телефон, кнопки магазинов и текст «Загрузка…», пока грузится Flutter.
- **Т-SEO-2.** Блок `<noscript>` содержит краткий текст о компании и контакты.
- **Т-SEO-3.** В `web/` лежат `robots.txt` и `sitemap.xml`.
- **Т-SEO-4.** Если Flutter не загрузился (старый браузер), пользователь всё равно видит контакты и ссылки на магазины.

> ⚠ **Решение заказчика:** по поисковикам сайт на Flutter будет хуже текущего. Если поиск для бизнеса критичен, нужно допустить отдельный статический лендинг. Это нарушит цель Ц3 в малом объёме: 5 HTML-страниц без логики.

### 4.3. Поддерживаемые платформы

| Уровень 1 (ошибка блокирует выпуск) | Web: Chrome, Edge, Яндекс Браузер, Safari (macOS, iOS), Firefox — последние 2 версии | — |

## 5. Функциональные требования

Обозначения: **[О]** — обязательно в версии 1.0, **[Ж]** — желательно.

### 5.1. Сайт (модуль `site`)
- **FR-S1 [О]** Главная страница: описание, преимущества, кнопка «Заказать обед», кнопки магазинов (только в браузере).
- **FR-S2 [О]** Страницы «О компании», «Доставка», «Как заказать», «Контакты». Тексты переносятся из текущего сайта (⚠ сверить с `website.js`).
- **FR-S3 [О]** Страница `/install`:
  - ссылки на Google Play, App Store, RuStore и APK;
  - инструкция по установке PWA для Chrome/Android и отдельно для Safari/iOS;
  - кнопка «Продолжить в браузере».
- **FR-S4 [О]** Ссылки «Политика конфиденциальности» и «Поддержка». Они обязательны для магазинов.

### 5.2. Вход и учётная запись (модуль `auth`)
- **FR-A1 [О]** Вход по логину и паролю через метод 1С `User/login`. Сервер возвращает токен.
- **FR-A2 [О]** Самостоятельная регистрация с подтверждением кодом из письма. Логика как сейчас (⚠ сверить методы с кодом).
- **FR-A3 [О]** Восстановление пароля. Завершается в браузере на `/reset-password`, как в шаблоне NewProject.
- **FR-A4 [О]** Смена email с подтверждением.
- **FR-A5 [О]** Выход. Токен удаляется на устройстве. Желательно, чтобы 1С тоже его отзывал (раздел 9).
- **FR-A6 [О] Удаление аккаунта.** Доступно из профиля: подтверждение → вызов метода 1С → выход. Это требование Apple (раздел 10.1).
- **FR-A7 [О]** Автозаполнение логина и пароля через `AutofillGroup` и `autofillHints`. Работает одинаково с менеджерами паролей браузера, Android и iOS.

### 5.3. Меню (модуль `menu`)
- **FR-M1 [О]** Загрузка `dishes.json` и дат, доступных для заказа (`Orders/menudates`).
- **FR-M2 [О]** Выбор дня или недели. Категории блюд с синхронной прокруткой: вкладки категорий связаны со списком.
- **FR-M3 [О]** Карточка блюда: фото, состав и вес (по данным JSON), цена, выбор количества.
- **FR-M4 [О]** Кэширование фото через `cached_network_image` в приложениях и через кэш браузера на Web.
- **FR-M5 [Ж]** Ссылка «Скачать меню в Excel» через `url_launcher`.

### 5.4. Корзина и заказ (модули `cart`, `orders`)
- **FR-C1 [О]** Корзина на несколько дней. По каждому дню отдельные позиции и итог.
- **FR-C2 [О]** Расчёт по правилам клиента: скидка, дневная дотация, минимальная сумма оплаты сотрудника, лимиты на день или неделю, минимальная сумма заказа. Подробности в разделе 7.
- **FR-C3 [О]** Отправка заказа (`Orders/basket`). Формат запроса совпадает с текущим (⚠ сверить: отправляются ли пустые дни). Сообщение «Заказ принят» показывается только после ответа сервера.
- **FR-C4 [О]** Черновик корзины сохраняется между запусками через `shared_preferences` (на Web — localStorage). Это отступление от шаблона NewProject, раздел 8, ADR-3.
- **FR-C5 [О]** При ошибке сети показывается понятное сообщение и кнопка «Повторить». Корзина не теряется.
- **FR-O1 [О]** История заказов.
- **FR-O2 [О]** «Повторить заказ»: перенос позиций прошлого заказа в корзину на выбранный день.

### 5.5. Профиль и служебные функции
- **FR-P1 [О]** Данные клиента из 1С: ФИО, организация, условия (скидка, дотация, лимиты).
- **FR-P2 [О]** Экран «О приложении»: версия, ссылки на политику и поддержку.
- **FR-P3 [О] Проверка минимальной версии.** При запуске приложение запрашивает у 1С или из `version.json` на сайте минимальную поддерживаемую версию. Если текущая версия ниже, показывается экран «Обновите приложение» со ссылкой. Этот механизм одинаков на всех платформах. На Web обновление происходит при перезагрузке страницы.

## 6. Нефункциональные требования

### 6.1. Безопасность (риск 1: хранение пароля)
- **NFR-SEC-1 [О] Пароль на устройстве не хранится.** Пароль используется только в момент входа и сразу удаляется из памяти. Текущий подход с повторным входом по сохранённому паролю (`refreshUserOrders(login, password)`) не переносится.
- **NFR-SEC-2 [О]** Обновление данных пользователя происходит только по токену. От 1С нужен метод «профиль по токену» с полными данными (раздел 9).
- **NFR-SEC-3 [О]** Токен хранится в `flutter_secure_storage`. На Android и iOS это системное защищённое хранилище, на Web — шифрованное хранилище браузера. Все принимают, что на Web защита слабее.
- **NFR-SEC-4 [О]** Если сервер отвечает 401 или «токен недействителен», данные сессии удаляются и открывается экран входа.
- **NFR-SEC-5 [О]** Все запросы идут только по HTTPS. В приложении нет секретных ключей.
- **NFR-SEC-6 [О]** Персональные данные обрабатываются по 152-ФЗ: есть политика конфиденциальности и согласие при регистрации.

### 6.2. Адаптивность (цель Ц2)
- **NFR-UI-1 [О]** Размеры экрана по шаблону NewProject: узкий до 600, средний 600–1023, широкий от 1024 логических пикселей. Раскладка выбирается только через `LayoutBuilder`.
- **NFR-UI-2 [О]**
  - Узкий экран: нижняя навигация, одна колонка.
  - Средний: боковая навигация (`NavigationRail`).
  - Широкий: меню и корзина видны одновременно, в две колонки.
- **NFR-UI-3 [О]** Страницы сайта адаптивны при ширине 360–1920 px. Текст ограничен шириной около 1200 px.
- **NFR-UI-4 [О]** Работает клавиатура (Tab, Enter, Esc), системная кнопка «Назад», прокрутка колесом мыши и изменение размера окна.
- **NFR-UI-5 [О]** Цвета и шрифты задаются одной темой Material 3. Цвета берутся из текущих CSS-переменных (⚠ сверить с `css/variables/_colors.css`).
- **NFR-UI-6 [О]** Язык интерфейса — русский. Все тексты хранятся в одном месте, чтобы потом можно было добавить другие языки.

### 6.3. Производительность
- **NFR-PERF-1 [О]** В браузере HTML-экран загрузки появляется быстрее чем за 1 секунду. Главная страница становится доступна быстрее чем за 4 секунды на мобильном 4G при первом входе и быстрее чем за 1,5 секунды при повторном.
- **NFR-PERF-2 [О]** Приложение из магазина открывает меню быстрее чем за 2 секунды, если сеть работает.
- **NFR-PERF-3 [Ж]** Попробовать сборку WebAssembly (`--wasm`) и выбрать более быстрый вариант по замерам.

### 6.4. PWA
- **NFR-PWA-1 [О]** В `web/manifest.json` указаны название, иконки (в том числе maskable), цвета, `display: standalone` и портретная ориентация.
- **NFR-PWA-2 [О]** Service worker минимальный. Он нужен для установки и кэширования статических файлов, данные не кэширует. Работа с данными без интернета не предусмотрена (NewProject).
- **NFR-PWA-3 [О]** Подсказка по установке для iOS показывается в Safari, если приложение не установлено. Это часть экрана `/install` и баннера, код находится в `distribution.dart`.

## 7. Бизнес-логика корзины (риск 4)

- **BL-1 [О]** До начала разработки корзины (этап 1) составляется документ `docs/pricing-spec.md`. В нём описан каждый параметр клиента из 1С: скидка, дотация, `MinimumPaymentАmount` (⚠ ключ с кириллической «А»), лимиты, минимальный заказ. Для каждого параметра указаны смысл, порядок применения, округление и не менее 3 примеров расчёта. Источник — текущие `state.js` и `renderCart.js`. Документ согласует заказчик.
- **BL-2 [О] Итоговую сумму определяет сервер.** Расчёт в приложении нужен только для предварительного показа. Желательно, чтобы 1С пересчитывал корзину и возвращал итог при отправке (раздел 9). Если 1С посчитал иначе, приложение показывает суммы 1С.
- **BL-3 [О]** Расчёт написан в отдельном модуле на чистом Dart `lib/features/cart/pricing.dart`. Модуль не зависит от Flutter и сети. Шаблон NewProject разрешает тесты для критичных расчётов.
- **BL-4 [О]** Модульные тесты покрывают все примеры из `pricing-spec.md` и особые случаи: дотация больше суммы дня, достигнут лимит, пустой день, скидка вместе с дотацией. `flutter test` обязателен в CI.
- **BL-5 [О]** Перед выпуском результаты сравниваются со старым сайтом не менее чем на 10 реальных корзинах.

## 9. Что нужно доработать в 1С

## 10. Публикация в магазинах

### 10.1. App Store (риск 2)
- **ST-iOS-1 [О]** Аккаунт Apple Developer (99 $ в год). Рекомендуется аккаунт **организации**, для него нужен номер D-U-N-S. **До начала этапа 6 заказчик решает, на кого оформлен аккаунт и как он оплачивается из РФ.**
- **ST-iOS-2 [О]** Для сборки нужен Mac с Xcode или облачная сборка (GitHub Actions на macOS, Codemagic).
- **ST-iOS-3 [О]** Удаление аккаунта внутри приложения (FR-A6) — правило Apple 5.1.1(v).
- **ST-iOS-4 [О]** Для проверки Apple нужна тестовая учётная запись (API-11) и описание, как ей пользоваться.
- **ST-iOS-5 [О]** Приложение должно быть полноценным нативным, а не обёрткой над сайтом (правило 4.2). Flutter это выполняет.
- **ST-iOS-6 [О]** Заполняются политика конфиденциальности (URL) и раздел App Privacy (какие данные собираются).

### 10.2. Google Play (риск 3)
- **ST-AND-1 [О]** Рекомендуется аккаунт **организации**. Для новых личных аккаунтов обязательно закрытое тестирование: не менее 12 тестировщиков в течение 14 дней. Если аккаунт будет личным, в план закладывается 2–3 недели и список тестировщиков.
- **ST-AND-2 [О]** Формат AAB, подпись через Play App Signing. Ключ загрузки хранится в секретах CI и в резервной копии у заказчика.
- **ST-AND-3 [О]** Приложение нацелено на актуальный уровень API, который требует Google Play на момент публикации.
- **ST-AND-4 [О]** Заполняются форма Data Safety, возрастной рейтинг и политика конфиденциальности.

### 10.3. RuStore и APK
- **ST-RU-1 [О]** Публикация в RuStore с той же подписью. APK для прямой загрузки лежит на `/install`.
- **ST-RU-2 [О]** Приложение не использует Google Play Services. Одна сборка работает на устройствах без сервисов Google: Huawei, устройства с RuStore.

### 10.4. Материалы для магазинов (готовит заказчик с разработчиком)
Иконка 1024×1024, скриншоты для телефона и планшета, короткое и полное описание, ключевые слова, URL политики и поддержки, тестовая учётная запись.

## 11. Инфраструктура, сборка и переход со старого PWA

- **INF-1 [О]** Caddy отдаёт Web-сборку. Все адреса без файла отдают `index.html`, кроме `/data/*`. Для `index.html`, `flutter_bootstrap.js` и `version.json` отключено кэширование, для остальных файлов сборки включено долгое кэширование.
- **INF-2 [О]** Окружения: `test.obedmoscow.ru` (тестовое) и `obedmoscow.ru` (рабочее). Адрес 1С и окружение задаются через `--dart-define`.
- **INF-3 [О]** GitHub Actions:
  - при каждом изменении: `flutter analyze`, `flutter test`;
  - при выпуске: сборка Web с публикацией на тестовый сайт, сборка AAB и APK, сборка iOS на macOS.
  - Ключи подписи хранятся в GitHub Secrets.
- **INF-4 [О]** Ежедневный бэкап на FTP сохраняется.
- **MIG-1 [О] Отключение старого service worker.** Новая сборка размещается по тем же адресам. Старый `sw.js` заменяется версией, которая удаляет все свои кэши, снимает регистрацию и перезагружает страницу. Иначе у пользователей старого PWA останется закэшированная старая версия.
- **MIG-2 [О]** Параллельная работа: новая версия сначала работает на `test.obedmoscow.ru`, затем на рабочем домене. Не менее 2 недель старый сайт доступен по резервному адресу.
- **MIG-3 [О]** Старый APK в `data/download` заменяется новым. Заказчик подтверждает, что старый APK можно убрать (⚠ выяснить, что это за APK).
