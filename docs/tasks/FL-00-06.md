## Что сделано

### Идентификатор устройства

| Клиент | Создание и хранение | Передача |
|---|---|---|
| Сайт/PWA | `getDeviceId()` читает `localStorage.DEVICE_ID`; при отсутствии создаёт UUID через `crypto.randomUUID()`, затем `crypto.getRandomValues()`, затем fallback на `Math.random()` и время. Logout очищает авторизационные данные, но не удаляет этот ключ. | Bare UUID передаётся как `deviceId` в `/User/login`, а также в регистрацию и смену почты. При токеновом обновлении профиля отправляется прежний `deviceId`. |
| Mob | При инициализации сеансового контекста формирует `New3_` + `СистемнаяИнформация.ИдентификаторКлиента` в `ПараметрыСеанса.ИдКлиента`. Проверка его долговременного хранения требует платформенного запуска и здесь не подтверждена. | Идентификатор используется в SOAP-вызовах заказов/меню и передаётся в HTTP-запросы регистрации/смены почты вместе с логином и паролем. |

SOAP-обработчик Zak снимает `New2_` и `New3_` перед серверной привязкой; ветки `New_` и `New1_` сейчас возвращают запрет до последующего кода снятия префикса. HTTP-обработчики регистрации и email-change снимают `New3_`, валидируют оставшийся UUID длиной 36 и используют его для проверки/записи привязки.

### Авторизация, сессия и обновление профиля

- Начальный сайт-вход — POST `/User/login` с `login`, `password`, `deviceId`; сайт добавляет `selfRegistration: true`. Сервер проверяет пользователя по коду, пароль (как сохранённое значение или SHA-256), признак запрета доступа и затем доступ устройства.
- В режиме старого учёта, если записи пользователя/устройства нет, сервер создаёт разрешённую привязку. Для учёта сотрудников имеющаяся привязка должна быть разрешена и указывать на сотрудника без пометки удаления; неизвестное устройство в обычном login-пути записывается с запретом доступа и запускает запрос активации. При `selfRegistration: true` сначала выполняется проверка состояния саморегистрации, поэтому этот поток может вернуть `registration_required` до общей проверки устройства.
- При успешном входе создаётся токен GUID без дефисов, записываемый в `РегистрСведений.СеансыПользователей` вместе с пользователем и текущим сотрудником. В коде валидность токена ограничена записями не старше 86400 секунд. Это непрозрачный токен, не JWT.
- Сайт сохраняет `authToken` и `userData` в `localStorage`; логин и пароль для повторного обновления заказов хранятся отдельно в `sessionStorage`. При загрузке сохранённого профиля сайт запускает фоновое обновление через тот же `/User/login`; профиль перезаписывается ответом при успехе. Logout удаляет токен/профиль и session credentials, но оставляет `DEVICE_ID`.
- Токеновый запрос сайта содержит `{token, deviceId}`. Сервер проверяет наличие `deviceId` в теле, затем валидирует токен и восстанавливает пользователя/сотрудника из регистра сеансов. В этой ветке код не сравнивает переданный `deviceId` с устройством, записанным в привязке. Отдельные операции смены почты проверяют и токен, и `deviceId`/разрешённую привязку.
- В обработчике User/login поле `token` включается в ответ и присваивается при парольном входе; на ветке обновления по токену новый токен не создаётся. Сайт сохраняет прежний токен как fallback, если ответ не содержит нового.

### Совместимость и открытые вопросы

- Сайт отправляет в HTTP login bare UUID. Mob формирует `New3_`-префикс для SOAP и HTTP регистрации/email-change; SOAP Zak и эти HTTP-обработчики его нормализуют.
- Общий HTTP User/login требует `deviceId`, но не снимает `New3_` до вызова `ИдКлиентаДоступРазрешен`; также саморегистрационная предварительная проверка получает присланное значение. Поэтому нельзя считать, что формат Mob `New3_<UUID>` совместим с `/User/login` без дополнительного подтверждения/проверки. В текущем сайте этот нюанс не проявляется, поскольку отправляется bare UUID. Сервер не менялся.
- Статически выявленная токеновая ветка принимает `deviceId`, но не использует его для проверки привязки. Это описание исходника, не вывод о фактически доступной атаке или серверном поведении; поведение не запускалось.
- До Flutter-реализации требуется определить канонический формат `deviceId` для HTTP-вызовов и согласовать необходимость проверки привязки на token refresh. Не подменять это решение предположением; контракты и обратную совместимость зафиксировать отдельной задачей до изменения кода.
