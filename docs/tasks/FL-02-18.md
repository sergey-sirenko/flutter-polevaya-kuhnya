# FL-02-18 — Подготовить демонстрационную учётную запись

## Назначение

- Бизнес-цель: предоставить проверяющим Apple и Google рабочий полный сценарий на тестовых данных без раскрытия персональных данных обычных пользователей.
- Требования ТЗ: API-11, ST-iOS-4, §10.4; дорожная карта §5.2; C-05.
- Модуль: данные тестового пользователя рабочей ИБ и инструкция проверяющему для будущей FL-07-09.
- Ответственный: владелец рабочей базы — подтверждение данных и полномочий; агент — протокол и проверка в разрешённом объёме.

## Входные условия

- Зависимые задачи: FL-00-14d (существующая тестовая учётная запись и заказ), FL-02-17f (ошибки/CORS); результат нужен FL-05-18, FL-07-09/16.
- Контракт: существующий `V1/User/login`; отдельная тестовая база/API не создаются.
- Окружение: тестовые пользователи в рабочей ИБ; поддомен Flutter не изолирует данные.
- Ограничения: обычных пользователей и их данные не использовать; не записывать в документы пароли, токены, коды и персональные данные; не создавать заказы или учётные записи без отдельного указания. Исходники Zak и сайт не меняются.

## Оценка перед выполнением

- Оцениваемый объём: вся подзадача.
- Сложность: 5/10.
- Трудоёмкость: средняя, ≈2% суммарных трудозатрат этапа 2.
- Рекомендуемая категория LLM: средняя.
- Основание: контракт и одна тестовая запись уже существуют; требуется сопоставить роли, данные и полный сценарий, а затем проверить его. Решение владельца базы и доступность данных — внешнее ожидание сверх трудозатрат.

## Что сделано

- По FL-00-14d: пользователь предоставил тестовые реквизиты, контролировал почту и сам создал тестовый заказ. API вернул успешный login и один заказ с датой 30.09.2026. Прямого чтения ИБ не было; роль и организация не проверялись.
- По FL-02-17f: парольная ветка после hotfix проверялась лишь на отказе с вымышленными реквизитами; успешный вход после обновлений ИБ не проверялся.
- У владельца запрашивались принадлежность записи/заказа, роль/организация и допустимость показа проверяющим. Секреты при этом не запрашивались.
- Пользователь ответил «да используй» на запрос о существующем тестовом пользователе, заказе и показе проверяющим. Это принято как разрешение использовать именно этот тестовый набор. Позже пользователь указал, что роль и организация не важны.
- Пользователь уточнил, что роль и организация не важны, а для входа достаточно выданных им реквизитов. Реквизиты не сохранены в проекте.
- Два read-only запроса login к актуальному API с ранее зарегистрированным `deviceId` вернули HTTP 200, `success:true`, профиль и токен. В обоих ответах `user.order` — пустой массив. Значения профиля и токена не выводились и не сохранялись. Заказы не создавались.
- После сообщения пользователя о создании заказов на 29.09 и 30.09 повторный login вернул оба заказа со статусом «Доступен», по две позиции, с `finalPayable`. Даты и агрегированные признаки проверены, содержимое профиля/позиций не выводилось. Инструкция: [demo-account.md](../demo-account.md).
