## Что сделано

### Отправка сайта

Сайт отправляет `POST /Zakaz_http/hs/Obmen/V1/Orders/basket` с JSON `{token, order}`. В `order` включаются все дни меню с `hasDelivery`, разрешённые `menudates`; для каждого дня передаются `date` в виде `YYYY-MM-DDT00:00:00` и `dishes`. Строка блюда содержит `dish`, `name`, `quantity`, `DiscountClient`. Пустой `dishes: []` передаётся намеренно как состояние дня, а отсутствие доступных дней прекращает отправку с клиентской ошибкой.

Сайт принимает HTTP 200 и проверяет `success`; при успехе использует возвращённый `order` для профиля. HTTP 400 считается ожидаемым бизнес-ответом и превращается в сообщение `error`; прочие неуспешные статусы считаются ошибкой транспорта. Клиент перед отправкой получает `menudates` по `POST /Orders/menudates` и учитывает `isOrderDayAllowed`.

### Обработка Zak

`ШаблонOrderBasket` требует непустой JSON-объект, `token` и `order`; проверяет токен и пользователя. Для каждого дня сервер проверяет `Документы.ЗаказПокупателя.ПриемЗаказаДоступен`. Недоступный день пропускается. Если день пуст и существующего заказа нет, он также пропускается; если заказ существует, пустой список может очистить его состав через `ЗаписатьЗаказ`.

Каждый `dish` преобразуется в ссылку `Справочники.Номенклатура` по UUID; отсутствующее блюдо возвращает ошибку. `ОбменДанными.ЗаписатьЗаказ` повторно получает актуальное меню, пересчитывает цены, сумму доставки, процентные и дневные скидки, очищает/заполняет строки заказа и записывает дату актуальности. Клиентская цена не является источником истины.

При конкурентном изменении сервер сравнивает `ДатаАктуальности` и может вернуть сообщение о заказе, изменённом в другом сеансе; запись также проверяет доступность дня, лимиты и прочие правила в вызываемом коде. Точная транзакционность и полный перечень бизнес-ошибок без runtime не подтверждены.

### История и повторный запрос

История сайта приходит в объекте `user.order` из ответа `User/login` или обновления профиля тем же endpoint: `refreshUserOrders(login,password)` и `refreshUserDataByToken(token)`. Перед переносом истории в корзину сайт повторно вызывает логин с сохранёнными в `sessionStorage` реквизитами; если их нет, остаются кэшированные данные.

Сервер `ПолучитьДанныеЗаказовПользователя` выбирает непомеченные к удалению документы начиная с переданной даты (по умолчанию начало текущей недели). Для обычного пользователя фильтр идёт по `Пользователь`; для новой формы — по `Пользователь` и текущему `Сотрудник`. Для каждой даты формируются `date`, `weekType`, `changes`, `status`, `dishes`, `discount`, `sum`. Строки блюда содержат `dish`, `name`, `menunumber`, `quantity`, `sum`, `DiscountPercentage`, `DiscountClient`.

Статусы вычисляются из проведения, признака выполнения, доступности редактирования и текущей даты: `Нет заказа`, `Выполнен`, `Доступен`, `Готовится`, `Доставка`, либо `Неизвестно`. В ответ попадают только даты, где найдена хотя бы одна положительная строка блюда; дни с пустым заказом не становятся исторической записью. `weekType` определяется сравнением номера недели сервера с датой заказа, поэтому календарный переход требует отдельной проверки.

В UI история используется для просмотра и переноса открытых заказов обратно в корзину. Перенос ищет блюдо сначала по `dish`, затем по имени в дне и глобально; несовпадение меню может дать пропущенную позицию. Закрытые дни остаются доступными для просмотра, но сервер не принимает их изменение.

### Mob/SOAP

Mob не использует этот HTTP endpoint для штатного обмена. `ОбменДанными.ОбменЗаказамиПериод` собирает документы по датам из `АктуальностьДанныхЗаказы`, сравнивает `ДатаАктуальности`, выгружает изменения через SOAP `ОбменЗаказами` с `ИдКлиента` и `СотрудникКод`, а недостающие дни добавляет в `МассивДнейЗагрузка`. Пустые массивы заказов/дней означают отсутствие работы; отдельный `ЗагрузитьЗаказы` применяет ответ сервера. Это иной транспорт и модель актуальности, но общий документ `ЗаказПокупателя`.

### Черновой контракт, не утверждённый

| Операция | Запрос/ответ | Известные ошибки и ограничения |
|---|---|---|
| `Orders/menudates` | `{token}` → `{success,message,menudates[]}` | Пустое/неверное JSON, отсутствует/устарел token, только доступные дни |
| `Orders/basket` | `{token,order:[{date,dishes[]}]}` → `{success,message,order[]}` | Неверное тело, token, отсутствует корзина, блюдо не найдено, день закрыт, конфликт изменения, серверная ошибка |
| `User/login` / refresh | `{login,password,deviceId}` или `{token,deviceId}` → профиль с `user.order` | Неверные реквизиты/токен, ограничение устройства; повторный запрос обновляет историю |

Форматы и коды являются черновым описанием исходников. Нельзя считать доставку заказа, окончательную сумму или атомарность подтверждёнными без тестового пользователя и серверного ответа.
