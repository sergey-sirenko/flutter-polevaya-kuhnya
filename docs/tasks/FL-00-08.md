## Что сделано

### Результат сверки

Метаданные `Zak/Konf/HTTPServices/Obmen.xml` объявляют для шаблона `/V1/User/{ИмяМетода}` методы HTTP POST, GET и OPTIONS. BSL-диспетчер `ЗапросUserPOST` фактически направляет только следующие имена методов:

- `login` → `ОбменHTTP.ШаблонUserLogin`;
- `emailchangestatus`, `emailchangestart`, `emailchangeresend`, `emailchangeconfirm` → `ДоступСотрудниковКлиентов.ИзменениеПочтыHTTP`;
- `registrationstatus`, `registrationstart`, `registrationresend`, `registrationconfirm` → `ДоступСотрудниковКлиентов.РегистрацияHTTP`;
- `activatedata` → `UserActivateData`.

GET-диспетчер содержит только `activate`, `message` и `test`; OPTIONS возвращает CORS-заголовки. Ни один из этих маршрутов не является восстановлением, сменой или установкой нового пароля. Неизвестное имя метода получает ответ неизвестного метода.

`ШаблонUserLogin` принимает первоначально `login`, `password`, `deviceId` (либо `token`, `deviceId` для обновления профиля), проверяет существующий пароль и возвращает ошибку при неверных данных. В исходниках нет ветки, которая отправляет код по email/телефону, принимает код восстановления или сохраняет новый пароль.

Клиент сайта вызывает только `User/login` для входа и повторной проверки сессии. Форма содержит поля кода клиента и пароля; найденная подсказка сообщает: «Получите код клиента и пароль у нашего менеджера». Кнопки, маршрута и клиентского метода «забыли/восстановить пароль» не найдено. Credential Management API лишь предлагает браузеру сохранить или подставить уже имеющийся пароль и не является восстановлением.

### Черновой вывод, не утверждённый контракт

Текущий API не предоставляет восстановление пароля. Нельзя объявлять поля, коды, сроки, лимиты или ответы такого потока до отдельного решения по серверу. Реальные доставка писем/SMS, изменение пароля и безопасность сценария исходниками не подтверждены.

### Обязательная следующая серверная задача и браузерный сценарий

До реализации Flutter требуется отдельная задача для владельца Zak: выбрать канал подтверждения (email или иной), определить привязку к организации/сотруднику и `deviceId`, срок и число попыток кода, лимиты повторной отправки, единоразовость токена, инвалидирование старых сессий и формат ошибок. После утверждения контракта нужен контролируемый браузерный сценарий на тестовой учётной записи рабочей базы: запрос восстановления, получение кода в согласованном тестовом канале, установка нового пароля, вход новым паролем, проверка отказа старого пароля и повторного/просроченного кода. Этот сценарий не выполнялся.
