# FL-00-14d — Подготовить тестовых пользователей рабочей базы и проверку CORS

## Назначение

- Бизнес-цель: подготовить безопасный интеграционный контур Flutter через существующий API 1С.
- Требования ТЗ: FL-00-14, отдельный origin `flutter-test.obedmoscow.ru`, без отдельной базы 1С.
- Модуль: тестовые пользователи рабочей базы, тестовые заказы, контролируемая почта и CORS.
- Ответственный: владелец рабочей базы совместно с исполнителем аудита.

## Входные условия

- Зависимые задачи: FL-00-05–FL-00-13, FL-00-14a–FL-00-14c.
- Нужные контракты и решения: черновой API-контракт FL-00-05; решение пользователя от 26.09.2026 использовать тестовых пользователей рабочей базы, не создавать отдельный API/базу.
- Окружение: отдельный HTTPS-origin `https://flutter-test.obedmoscow.ru`; его `/api/*` и `/data/*` пока намеренно отвечают 503.
- Исходные ограничения документальной подготовки: не запускать приложения, API, рабочую базу, почту или тесты; не создавать заказы/письма/пользователей. Позже пользователь явно разрешил ограниченный login, тестовую регистрацию с контролируемой почтой и CORS preflight. Заказы и серверная схема не создавались; исходники и конфигурация не менялись.

## Что сделано

- Подтверждено, что отдельная 1С и отдельная рабочая база не требуются; Flutter должен использовать обезличенные тестовые учётные записи рабочей базы.
- Зафиксировано, что поддомен изолирует Web-размещение, но не данные 1С; до сценариев нужно определить учётные записи, роли/организации, владельцев тестовых заказов и контролируемый mailbox.
- Подготовлен будущий порядок проверки: read-only авторизация и меню; затем история/заказы; отдельно регистрация и смена email через контролируемую почту; preflight и credentialed CORS с `https://flutter-test.obedmoscow.ru`; ошибки сверять с FL-00-05. Записи и отправку заказов выполнять только после отдельного разрешения и с заранее определённым откатом.
- В исходниках найдено правило маркировки тестового заказа: при экспорте `ЗаказПокупателя` заказ пользователя, в коде которого встречается `test`, помечается загруженным, снимается с регистрации обмена и не выгружается в 1С 7.7. Это только механизм обмена; он не определяет конкретного пользователя, организацию или допустимость заказа для Flutter.
- Документы саморегистрации требуют тестовые организации с учётом сотрудников и без него, контролируемый почтовый ящик и исключение адресов реальных клиентов; сценарии включают проверку двух клиентов, лимитов, кодов и блокировок. Идентификаторы таких организаций/пользователей в исходниках не указаны.
- По указанию пользователя выполнен один `POST /Zakaz_http/hs/Obmen/V1/User/login` с предоставленными реквизитами и новым случайным `deviceId`; пароль, email, токен, логин и текст ошибки в карточку не записывались. Ответ: HTTP 400, `success:false`, `code:registration_required`, без объекта `user`. Это согласуется с веткой регистрации устройства/сотрудника, но не подтверждает доступ к профилю и заказам.
- В ответе login присутствовали `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Credentials: true`, разрешённые заголовки и методы. HTTP OPTIONS preflight на существующий API `hleb-sol.su` вернул 200 для POST/JSON. Проверка браузером не выполнена: встроенный браузер заблокировал открытие тестового origin (`ERR_BLOCKED_BY_CLIENT`); доступного другого браузера нет. API вызовы шли к существующему API, не к новому vhost.
- После подтверждения пользователя, что устройство разрешено к регистрации и почтовый ящик контролируется, `registrationstart` вернул HTTP 200 `code_sent`. Пользователь получил и передал код, что подтвердило доставку письма на его стороне; код, email и `requestId` в карточку не записаны.
- Для этого первого запроса случайный `deviceId` был создан во временном процессе и не сохранён; поэтому переданный пользователем код нельзя применить к подтверждению без риска неверно привязать запрос. Старый код не отправлялся серверу на проверку.
- По последующему указанию пользователя создан и сохранён тестовый `deviceId`: `5b354cbc-3acf-410f-9836-2d3c0dc70726`; повторные start, confirm и login использовали его.
- Повторный `registrationstart` с сохранённым `deviceId` вернул HTTP 200 `code_sent`, `retryAfter: 60`, `expiresIn: 600`; новый `requestId` сохранён только в текущем состоянии задачи, не в документах. Пользователь передал код для этого запроса, но `registrationconfirm` ответил HTTP 400 `ambiguous_employee`.
- В BSL подтверждение кода проверяется до поиска сотрудников. При нескольких сотрудниках с тем же email обработчик возвращает `ambiguous_employee` до создания нового сотрудника, записи привязки устройства и завершения запроса. Это подтверждено чтением исходника; к рабочей базе напрямую не обращались.
- По исправленному адресу `registrationstart` с сохранённым `deviceId` вернул HTTP 200 `code_sent`; `registrationconfirm` — HTTP 200 `registered`; затем `User/login` с тем же ID вернул HTTP 200 `success:true`, профиль и токен присутствовали. Сервер подтвердил регистрацию в рабочей базе; состав записи напрямую не проверялся. Токен и профиль не выводились и не сохранялись. Первый login вернул пустой/отсутствующий `user.order`; после сообщения пользователя о создании тестового заказа в старой версии сайта повторный login вернул один элемент `user.order`: дата `2026-09-30`, статус `Доступен`, одна позиция блюда. Это подтверждает, что заказ попал в ответ login; прямую запись в базе и другие заказы не проверяли.
- HTTP OPTIONS preflight для origin `https://flutter-test.obedmoscow.ru`, POST и заголовков `content-type,accept` вернул HTTP 200. Ответ разрешает `*`, методы включают POST, заголовки включают Content-Type и Accept, `Access-Control-Allow-Credentials: true`; browser CORS не проверялся. Для Fetch с credentials mode `include` wildcard несовместим; обычный login передаёт реквизиты в JSON и не использует cookie credentials.
- Новый vhost из FL-00-14c продолжает держать `/api/*` и `/data/*` в 503; проверенный login выполнялся к существующему API на `hleb-sol.su`, не к новому vhost.
