## Что сделано

### Общий транспорт

Операции идут POST JSON по `/Zakaz_http/hs/Obmen/V1/User/<метод>`, с UTF‑8, `Content-Type: application/json`, ответами HTTP 200 при успехе и HTTP 400 при ожидаемой бизнес-ошибке. Серверный формат результата регистрации: `success`, `code`, `message`, `error`; при успехе `error` пуст. Каждый запрос регистрации содержит `login`, `password`, `deviceId`, а операции email используют `token`, `deviceId`. Сервер повторно проверяет реквизиты и актуальную привязку на каждом шаге.

### Саморегистрация сотрудника

1. Сайт отправляет обычный `User/login` с `selfRegistration: true`. Если организация ведёт учёт сотрудников, а устройство не подключено, сервер возвращает `success: false`, `code: registration_required` без создания записи ожидания и без письма ответственному. Уже подключённое устройство продолжает обычный вход.
2. `registrationstart`: дополнительные поля `fullName` (до 50 символов) и `email` (до 100). Email нормализуется обрезкой пробелов и нижним регистром; проверяются две части адреса, домен с точкой и запрещённые управляющие/специальные символы. При успехе создаётся запрос в регистре и документ письма со статусом очереди, возвращаются `code_sent`, `requestId`, `retryAfter: 60`, `expiresIn: 600`.
3. `registrationresend`: принимает текущий `requestId`, сохраняет историю, помечает прежний незавершённый запрос этого пользователя и устройства как `superseded`, выдаёт новый `requestId` и тот же набор таймингов. Для неизвестного или чужого идентификатора возвращает `invalid_request`.
4. `registrationconfirm`: принимает `requestId` и строковый шестизначный `verificationCode`; код хранится только в виде хеша, действует 600 секунд, допускается пять ошибочных попыток. Ошибки дают `invalid_code`, затем `attempts_exhausted`; просроченный/заменённый запрос — `code_expired`.
5. При успешном подтверждении сервер повторно проверяет организацию, существующего сотрудника с такой почтой, блокировки и привязки. Если сотрудник найден, используется он; если нет — создаётся новый сотрудник с введённым ФИО и почтой. В регистре `ИдКлиентов` создаётся одна разрешённая привязка к устройству, запрос становится `completed`, возвращается `registered`; сайт закрывает форму и повторяет обычный вход.
6. Лимиты отправок: минимум 60 секунд между письмами, максимум пять за скользящий час отдельно для пары организация/почта и устройства. В ответе `rate_limited` присутствует `retryAfter`. Все операции выполняются транзакционно с блокировками; постановка письма в очередь не равна фактической доставке.
7. Серверные дополнительные коды: `invalid_credentials`, `invalid_request`, `invalid_profile`, `access_denied`, `ambiguous_employee`, `already_registered`, `registration_not_required`, `registration_unavailable`. Клиент сайта показывает текст ошибки, отсчитывает `retryAfter`, блокирует повтор во время ожидания и при отмене увеличивает поколение формы, очищает requestId и игнорирует поздний ответ.

### Смена email сотрудника

1. `emailchangestatus`: запрос `{token, deviceId}`. Сервер определяет пользователя и сотрудника по токену и разрешённой привязке, возвращает `email_change_status`, текущий `email` и `canChangeEmail`. Для организации без учёта сотрудников возвращается `email_change_not_allowed`; отсутствие регистра подтверждений даёт `canChangeEmail: false` или `email_change_unavailable` для операций изменения.
2. `emailchangestart`: добавляет новый `email`; при том же нормализованном адресе возвращает успешный `email_unchanged` без письма. Иначе проверяет занятость адреса другим сотрудником организации и лимиты, создаёт запись/письмо, возвращает `code_sent`, `requestId`, `retryAfter: 60`, `expiresIn: 600`.
3. `emailchangeresend`: принимает `requestId`, требует состояние `queued` и неизменившийся исходный адрес, заменяет незавершённые запросы сотрудника на новый. Старый код становится недействительным; новый requestId возвращается вместе с таймерами.
4. `emailchangeconfirm`: проверяет принадлежность requestId пользователю, сотруднику и устройству, срок 600 секунд и пять попыток. При правильном коде повторно проверяет занятость и записывает новую почту в одном потоке с завершением запроса; возвращает `email_changed` и новый адрес. Повтор последнего успешного подтверждения возвращает успех без повторной записи, если текущая почта совпадает.
5. Ошибки email: `invalid_request`, `invalid_credentials`, `access_denied`, `email_change_not_allowed`, `email_change_unavailable`, `invalid_email`, `email_in_use`, `request_stale`, `code_expired`, `invalid_code`, `attempts_exhausted`, `rate_limited`; ограничение содержит `retryAfter`.
6. Сайт не сохраняет промежуточный requestId/код в localStorage. Отмена формы очищает локальное состояние и закрывает её; generation/sequence-защита игнорирует поздние ответы. После успеха обновляются `userData.email` и отображение, токен, корзина и остальные данные сохраняются. `request_stale` возвращает форму к вводу нового адреса.

### Нерешённые вопросы

- Статический код подтверждает постановку письма в очередь, но не доставку; реальный почтовый и пользовательский сценарий не проверен.
- Совместимость `New3_` для HTTP login уже отмечена в FL-00-06; регистрация/email явно снимают этот префикс.
- Восстановление пароля и удаление аккаунта не входят в эту задачу и остаются FL-00-08/09.
