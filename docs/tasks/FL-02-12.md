## Что сделано

- В `Зак/docs/self-registration.md` каждый шаг требует `login`, `password`, `deviceId`; обработчик Zak проверяет реквизиты перед обработкой метода.
- Сайт передаёт пароль через объект открытой формы регистрации; отдельно существует старое хранение реквизитов в `sessionStorage` для обновления заказов. Эти механизмы не являются разрешённой моделью нового Flutter-клиента.
- У заказчика запрошен выбор между короткоживущим серверным контекстом и явно ограниченным хранением пароля только в памяти формы.
- Пользователь выбрал серверный контекст. В `Zak/docs/self-registration.md` закреплён контракт 1.1 `context_v1`: пароль у нового клиента нужен в `registrationstart`; `requestId` служит временным ключом для `resend`/`confirm` без пароля. Обычный вход до/после регистрации остаётся отдельной операцией.
- В модуле объекта `ДоступСотрудниковКлиентов` добавлены состояния `queued_context`/`completed_context`, проверка срока и устройства, смена ключа при повторной отправке без продления общего 600-секундного срока. Старый парольный режим `queued`/`completed` сохранён.
- Обновлены архитектурное решение C-01, API-указатель и общая карточка. Код прежнего сайта и Mob не менялся; их поток по-прежнему требует пароль на каждом шаге.
