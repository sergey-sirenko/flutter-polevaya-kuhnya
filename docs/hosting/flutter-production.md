# Основной сайт Flutter — FL-WEB-PROD-01

Решение владельца от 05.10.2026 заменяет прежнюю схему с `new.obedmoscow.ru`.

| Адрес | Назначение после переключения |
|---|---|
| `https://flutter-test.obedmoscow.ru/` | Разработка и пользовательская приёмка, APP_ENV=test |
| `https://obedmoscow.ru/` | Принятый Flutter-выпуск, APP_ENV=prod |
| `https://www.obedmoscow.ru/` | Существующий redirect на основной адрес |
| `https://test.obedmoscow.ru/` | Прежний сайт из сохранённого `/var/www/polewaya` |

Подготовлены исходники и конфигурация; переключение ещё не выполнено. Архив прежнего сайта остаётся подключён к рабочему API: это сохранённый интерфейс, а не изолированная тестовая база. История заказов хранится на сервере; локальные черновики и вход другого origin автоматически не переносятся. Сохранить старый сайт и его данные до проверки перехода.

## Приёмка на тестовом адресе

Сборка: `pwsh -File .\tools\build_web_test.ps1`. Пользователь запускает выкладку:

```powershell
pwsh -File .\tools\deploy_web_test.ps1 -SkipBuild
```

Проверить номер версии, главную/доставку/контакты, меню и фотографии, навигацию и перезагрузку вложенного маршрута, запуск с телефона. Проверка входа/истории/черновика — владельцем с согласованной тестовой учёткой; живые заказы в этот шаг не входят. Зафиксировать принятую версию и точный source commit. Новые изменения после приёмки сначала повторно направлять на Flutter test.

## Подготовка принятого production-выпуска

Зафиксировать только изменения задачи и отправить обычным push в существующий origin. Чистый checkout должен соответствовать принятому полному SHA. Скрипт намеренно отклоняет изменённое дерево и неподходящий SHA:

```powershell
pwsh -File .\tools\build_web_prod.ps1 -AcceptedCommit <полный-40-символьный-SHA>
```

Результат `build/web-prod`: отдельный APP_ENV=prod, production version URL, `release-manifest.json` с source SHA/версиями/SHA-256 каждого файла. Test-бинарник публиковать на основном домене нельзя. Минимум остаётся `0.1.0+1`, Android/iOS остаются null. Скрипт не публикует сборку.

## Первый перенос и возврат

Выполнять как отдельную подзадачу после пользовательской приёмки. Перед переносом повторно прочитать действующий Caddyfile и состояние каталогов. Не заменять весь Caddyfile двухдоменным фрагментом.

1. Сохранить `/etc/caddy/Caddyfile`, прежние ссылки/пути и текущий старый сайт в датированный резерв `/var/backups/flutter/`. Каталог `/var/www/polewaya/data` сохранить отдельно, с владельцем и правами; не перемещать, не заменять из Git и не очищать. FTP продолжает писать по прежнему пути.
2. Загрузить production в новый `/var/www/flutter-prod/releases/<source-SHA>-<build>/`; проверить каждое имя, размер и SHA-256 по manifest, права чтения Caddy и prod-policy. Существующую версию по этому пути не перезаписывать. Переключать `current` атомарной заменой symlink, записав предыдущую цель.
3. Составить полный кандидат Caddyfile: заменить только блоки apex и старого test фрагментом [production-sites.caddy](production-sites.caddy). Сохранить www redirect, Flutter test и остальные сервисы. Новый apex отдаёт `/data/*` из прежнего каталога без удаления префикса; отсутствующие assets/JSON отвечают 404, маршруты приложения получают index.html.
4. Выполнить `caddy adapt` и `caddy validate` полного кандидата. Установить его и выполнить `systemctl reload caddy` только после успешной проверки. Зафиксировать время, резерв, source SHA и цель current.
5. Проверить HTTPS четырёх адресов, prod/test environment и версии, хеши файлов, robots/sitemap, отсутствующий JSON (404), вложенный маршрут, menu JSON/фото и CORS данных. Сравнить данные/права до и после. Владелец проверяет ранее открытый основной сайт и установленный PWA, запуск Flutter, вход и сохранность истории.
6. При ошибке восстановить сохранённый Caddyfile, прежнюю цель current и reload после validate. Проверить основной и тестовые адреса. Runtime data из старого резерва не откатывать поверх более новых изменений.

Прежний worker `/service-worker.js` заменяется файлом снятия регистрации. Он не обслуживает fetch из старого кэша, не очищает localStorage/IndexedDB и не перезагружает открытый заказ. Уже открытая страница может оставаться старой до следующего посещения/обновления; клиентская приёмка обязательна. Снятие регистрации не является переносом пользовательских данных между двумя разными приложениями. Основание: [MDN unregister](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/unregister), [Caddy handle](https://caddyserver.com/docs/caddyfile/directives/handle).

## Последующие выпуски

Один source release: новая версия → сборка/выкладка на Flutter test → пользовательская приёмка с записанным SHA → отдельная production-сборка этого SHA → резерв, проверка manifest и переключение current. Caddy и архив повторно не менять без необходимости. Журнал каждого выпуска должен различать «подготовлен», «принят», «опубликован» и «возвращён».
