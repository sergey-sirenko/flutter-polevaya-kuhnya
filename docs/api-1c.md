## Примеры и доказательства

Дополнение контракта представления v0.4: [FL-06-20g](tasks/FL-06-20g.md#контракт-представления-v04) определяет необязательное `photo_version` и клиентское хранение версий фото. Клиент реализован локально, поле в выгрузке Zak требует отдельного поручения; серверная реализация и живая приёмка смены фото не подтверждены.

Формы JSON запросов/ответов и известные ошибки приведены в FL-00-05–07/11 и серверных документах по ссылкам выше. [Локальный набор ответов FL-01-14](test-responses.md) покрывает успех, пустые данные, старую/новую ошибку и целевой HTTP 401; рядом с каждой фикстурой указаны маршрут, статус и степень подтверждения. Это синтетические ответы для MockClient, а не утверждённый единый контракт или доказательство работы сервера. Перед бизнес-функцией примеры уточняются по её контрактной задаче.

Подтверждённые ранее ограниченные runtime-результаты находятся только в FL-00-14d: регистрация, парольный login, один существующий тестовый заказ в `user.order`, OPTIONS. Они не доказывают token refresh, расчёт суммы, отправку/повтор заказа, смену email, удаление или browser CORS. Сброс пароля исключён решением 27.09.2026 и не требует runtime-проверки API. Реальные реквизиты, коды, токены и содержимое профиля в примеры не включаются.

## FL-AUTH-05 — восстановление реквизитов входа

`POST V1/User/passwordrecovery` принимает только `email`; канонический [контракт v1.0](../../Zak/docs/password-recovery.md). Во Flutter `/reset-password` позволяет явно запросить письмо. Успех `credentials_queued` означает очередь, ошибки показываются по известным кодам без серверного текста. Этот сценарий заменяет прежнее решение об отсутствии функции; отправляет текущие реквизиты, не меняет пароль. Сначала пользователь загружает два модуля Zak, затем публикует Web +46.

## Снимок подготовки заказа — FL-UX-18

`POST V1/Orders/snapshot`, [Zak контракт v1.0](../../Zak/docs/order-snapshot.md), заменяет четыре обращения подготовки одним. Типизированный ответ: полный user с order/условиями, menudates, states, schemaVersion и ownerScope. `dates` ограничивает states; без dates — 14 календарных дат текущей/следующей недель сервера. При подготовке применяются только данные текущей сессии/операции после полной проверки, без промежуточной загрузки или повторных login/menudates/basketstate. Существующая отправка/проверки basket и неизвестного исхода сохраняются. Нет автоматического fallback на старые методы. Пользователь подтвердил загрузку обоих BSL-модулей; клиент Web +54 локальный, SSH/живая приёмка/конкурентная платформенная проверка отдельно. [Клиентская карточка](tasks/FL-UX-18c.md).
