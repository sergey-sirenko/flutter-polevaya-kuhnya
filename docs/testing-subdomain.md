## Почему отдельный адрес

- test.obedmoscow.ru уже обслуживает старую PWA и используется её процессом выпуска.
- Отдельный origin позволяет сравнивать версии без конфликта service worker, кэшей и localStorage.
- Не нужно перемещать рабочий сайт или менять его FTP/runtime-данные.
- Исходный ТЗ предполагает test.obedmoscow.ru. Новый адрес — уточнение тестового размещения, не изменение функциональности; зафиксировать принятие до настройки.

## FL-00-14c: Caddy и HTTPS — выполнено

Добавлен [отдельный bootstrap-vhost](../ops/flutter-test.bootstrap.Caddyfile). Он отдаёт служебный текст без Flutter, не обращается к 1С, возвращает 503 для /data и /api, отключает кэширование и добавляет noindex. Noindex не является ограничением доступа; служебная страница публична и не содержит бизнес-данных. До изменения сохранена копия `/var/backups/caddy/Caddyfile.before-flutter-test-20260926T141000Z` (режим `0600`, SHA-256 `27eb8a499f093afe9a9b514897d61297e9ffd9af678740e0d386cea165573f8f`). Активный `/etc/caddy/Caddyfile` SHA-256 `19fc073be643ba807fa1e6d4637cb3930047e602728725de485fbb778b44d3d6`.

Порядок настройки после подтверждения и готовности DNS:

1. Повторно сверить DNS, действующий Caddyfile и состояние старых сайтов.
2. Сохранить отдельную резервную копию конфигурации с датой и контрольной суммой.
3. Подготовить объединённый кандидат, добавляя только новый vhost. Не заменять существующий Caddyfile одним bootstrap-блоком.
4. Выполнить caddy validate для полного кандидата; при ошибке не применять.
5. Разместить проверенный кандидат и выполнить штатный reload Caddy. Не останавливать сервис.
6. Подтвердить публичный HTTPS-сертификат нового имени, HTTP → HTTPS, служебный ответ и заголовок noindex. При недоступности проверки явно отметить непроверенное.
7. Сверить сохранность прежних блоков и корней. При сбое восстановить сохранённую конфигурацию и reload; не менять данные сайта.
8. Записать резервную копию, активную конфигурацию и результаты. Остановиться.

Фактический результат FL-00-14c: полный кандидат и установленная конфигурация прошли `caddy validate`; Caddy `2.10.0` active после reload. HTTP вернул 308 на HTTPS; `curl` проверил TLS (verify result 0). `/` вернул 200 с ожидаемым текстом, noindex и no-store. `/api/test` и `/data/test` вернули 503. Контрольные GET production и старого test вернули 200. Исходники сайтов, runtime-данные, приложение и 1С не менялись. Временные файлы проверки удалены.

Caddy может выпускать и продлевать сертификат автоматически при корректных A/AAAA, доступных портах и настроенном имени. Конкретное получение сертификата проверяется после настройки. [Официальная документация HTTPS](https://caddyserver.com/docs/automatic-https)

## Последующее размещение Flutter

При наличии принятой Web-сборки использовать отдельный каталог /var/www/polewaya-flutter-test/releases/current и собственный процесс выпуска. Старый deploy-polewaya-test предназначен для другого клиента и подключает runtime-данные production, поэтому его нельзя запускать для Flutter без адаптации.

На этапе FL-06-14 служебный respond заменяется раздачей сборки с SPA-маршрутами. /data/* обрабатывается отдельно и не подменяется index.html. Загрузчики и version.json должны получать свежие версии; правила кэша сборки проверяются отдельно. [Официальный пример SPA для Caddy](https://caddyserver.com/docs/caddyfile/patterns#single-page-apps-spas)

## FL-00-14d: тестовые пользователи рабочей базы

**Решение пользователя 26.09.2026:** отдельный тестовый API и отдельная база не нужны; используем тестовых пользователей на рабочей базе 1С через существующий API.

Поддомен изолирует Web-размещение, но не данные 1С. До интеграционных сценариев зафиксировать тестовые учётные записи и организации, принадлежность тестовых заказов и контролируемую почту. Для операций использовать только эти учётные записи; обычные заказы и пользователей не затрагивать. Способ отличать тестовые заказы уточнить по существующим возможностям 1С, не вводить новую серверную схему без необходимости.

Адрес API подтвердить аудитом FL-00-05. Проверить CORS рабочего API для https://flutter-test.obedmoscow.ru; при необходимости изменить разрешённый список origin в отдельной согласованной подзадаче. Proxy как обход CORS не добавлять. Текущий анализ не отправляет запросов в 1С и не создаёт заказы.
