## 2. Принятый источник и границы

Единственный публичный GET `/version.json` на домене **Flutter** выбранного окружения, одинаковый для Android/iOS/Web:

| Окружение | Принятый `APP_VERSION_URL` |
|---|---|
| test | `https://flutter-test.obedmoscow.ru/version.json` |
| prod | `https://new.obedmoscow.ru/version.json` |

Это **обязательный параметр сборки**, добавленный FL-06-20o в AppConfig, Web/Android-скрипты и фикстуры; будущие iOS-сборки получают тот же источник среды. Его задают во всех трёх клиентах, не выводят из DATA_BASE_URL: меню/фото остаются на `https://obedmoscow.ru/data/`. Prod endpoint не считается доступным до отдельной выкладки. Поддомен test не изолирует базу 1С.

Минимум — единый для всех клиентов; способ получить новую сборку соответствует каналу установки. Политикой управляет владелец выпуска Flutter, не выгрузка меню Zak. Изменения 1С не предлагаются. Источник, исходный test-минимум и поведение ниже приняты владельцем; prod-порог и выпуск остаются отдельными решениями.

Запрос идёт через общий публичный транспорт, без токена, cookies приложения, логина/пароля и тела API. Нужен GET на явно проверенный HTTPS URL из конфигурации: без userinfo/fragment и без переходов на неожиданный origin; `Accept: application/json`. Транспорт не должен ограничивать этот запрос относительными путями базы меню и не должен автоматически добавлять авторизацию. Ошибки транспорта преобразуются в состояние проверки, а не сброс сессии.

Принят один запрос при холодном старте, общий deadline **5 секунд**, затем явная кнопка повтора; без постоянного опроса и бесконечных retries. Поздний ответ предыдущей проверки не перезаписывает результат новой. Успешный результат действует до следующей явной проверки/запуска; не обещает немедленную блокировку всех уже открытых вкладок при изменении серверного файла.

Клиент получает свежий ответ через уникальный служебный query `check` без персональных данных и серверную ревалидацию. Policy/version.json не попадает в offline/service-worker-кэш или постоянный локальный кэш. `no-cache` допускает хранение с обязательной ревалидацией, это не `no-store` ([MDN Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)); браузерное поведение нужно подтвердить в реализации. Не вводить обязательные нестандартные request headers, создающие лишний CORS preflight. Native читает тот же endpoint, Web должен иметь разрешённый CORS, если запрос окажется между разными origin; проверка CORS этого публичного файла отдельна от API.

## 3. Формат JSON

Корневые `version`/`build` сохраняются для существующих читателей и идентифицируют **размещённую Web-сборку**. Новый вложенный `policy` задаёт минимум и фактически доступные обновления. Пример ниже — **принятая начальная test-политика с идентификацией Web +8**, не опубликованный файл; при выпуске корень/release должны совпасть с фактической сборкой. Это не подтверждение совместимости всех прежних сборок:

```json
{
  "version": "0.1.0",
  "build": 8,
  "policy": {
    "schema": 1,
    "environment": "test",
    "minimum": { "version": "0.1.0", "build": 1 },
    "releases": {
      "web": {
        "version": "0.1.0",
        "build": 8,
        "url": "https://flutter-test.obedmoscow.ru/"
      },
      "android": null,
      "ios": null
    }
  }
}
```

Предлагаемый исходный минимум **0.1.0+1** консервативен: не блокирует Web +8 и локальный Android +4 до появления принятых мобильных выпусков. Его утверждение не заменяет их интеграционную приёмку. Для prod необходимо отдельно задать реальные версию/Web URL и утверждённый порог; копировать test-пример в prod нельзя.

| Поле | Правило |
|---|---|
| `version`, `build` | Версия размещённого Web; значения из текущего release артефакта, не из запроса клиента |
| `policy.schema` | Целое 1. Отсутствие/другая схема означает неизвестную политику |
| `policy.environment` | `test` или `prod`, обязано совпасть с конфигурацией клиента |
| `policy.minimum` | Обязательная пара version/build, общая для Android/iOS/Web |
| `policy.releases` | Объект с тремя обязательными ключами `web`, `android`, `ios` |
| Запись release | Пара version/build и HTTPS `url` принятого, доступного выпуска; `null`, если такого выпуска для канала нет |

Все version — три неотрицательных десятичных целых `major.minor.patch`, без prerelease, пробелов, ведущих нулей (кроме самого 0) и суффикса `+build`. Build — положительное целое JSON; строки, bool, дроби и отрицательные числа не принимаются. Числовые части ограничиваются диапазоном безопасных целых Dart/JS; платформенные ограничения номеров выпуска дополнительно проверяет процесс мобильной сборки. Неизвестные дополнительные поля игнорируются, но неверная обязательная структура отклоняет весь policy.

`minimum <= web release`, корневая пара точно равна `releases.web`; Web release обязателен для среды, публикующей этот файл. Любой ненулевой release обязан быть не ниже минимума. Native release `null` не означает, что существует новая APK/магазинная версия: локальный APK +4 не рекламируется как опубликованный. Ссылки прежних приложений и неподтверждённые APK не допускаются. URL проверяется по утверждённому allowlist доменов/продукта, без userinfo и произвольных редиректов; до выпуска магазинов записи mobile остаются null. Внешние адреса — только действие пользователя, никогда автопереход.

Старый JSON без policy — неизвестный минимум, а не требование обновиться. Нельзя использовать корневую «последнюю Web-версию» как минимум Android/iOS. Существующая +8 сама не получает новое поведение от добавления поля: потребуется новый код и отдельная выкладка.

## 4. Сравнение и состояния

Сравнение лексикографическое по числовому кортежу **(major, minor, patch, build)**. Build сравнивается лишь при равной version. Нет свёртки в одно число, сравнения строк и предположения, что высокий build заменяет высокий major/minor/patch. Неизвестные метаданные текущей сборки не заменяются корневой серверной версией.

| Условие | Общее состояние и результат |
|---|---|
| Первый запрос идёт | `checking`: краткий стартовый экран, бизнес-операции ещё не запускаются |
| Current < minimum | `required`: общий экран «Обновите приложение», вход/регистрация и операции меню/корзины/заказов недоступны до принятой совместимой версии |
| Current >= minimum и release текущего канала > current | `available`: совместимая работа разрешена; неблокирующая подсказка обновиться, пользователь может отложить |
| Current >= minimum и release <= current либо release null | `current`: работа разрешена; нет требования откатиться или ложного сообщения о наличии мобильного обновления |
| На первом запросе сеть/timeout/404/HTML/плохой JSON/схема/окружение/текущая версия неизвестны | `unknown`: сообщить, что версию проверить не удалось, дать повтор, разрешить продолжить по обычным правилам сессии/сети; не объявлять несовместимость |
| В этом процессе уже был валидный `required`, повтор закончился ошибкой | Последний подтверждённый required сохраняется с сообщением о сбое повтора; ошибка не является разрешением обойти известный минимум |

Разрешение при **первой** ошибке — принятое поведение по FL-06-13/W07; клиентская проверка не является защитой серверного API от старых клиентов. Обязательную серверную несовместимость можно обеспечить только отдельным серверным контрактом. В этой задаче такой контракт не предполагается.

После успешного повторного чтения с меньшим минимумом (например, согласованный откат) результат пересчитывается; намеренное понижение политики не запрещается монотонным локальным флагом. Не сохранять требование обновления бессрочно в localStorage. Пользователь может перезапустить приложение; при новом запуске снова действует правило первого запроса.

На required доступны повтор проверки, сведения о текущей/минимальной версии, поддержка/политика и действие обновления. Кнопка не даёт выполнять заказ, не очищает сессию/хранилище, не отправляет запросы Orders. Если для native нет опубликованного compatible release, показать отсутствие доступного выпуска и поддержку; не выдавать чужую/старую ссылку и не разблокировать приложение. **Порог нельзя повышать выше известных активных native-сборок, пока не опубликован пригодный путь обновления для их пользователей.** Исходная политика с минимумом +1 это ограничение не нарушает.

## 5. Обновление и сохранность

Все решения о current/available/required/unknown, запретах и сохранении — общие. Платформа определяется только в `core/platform/distribution.dart`; выбор записи release — часть распространения. Потребуется **предлагаемая ADR-9** в ARCHITECTURE для механизма действия обновления: Web перезагружается, native открывает проверенную ссылку выпуска. ADR пока не принята; условные Web-адаптеры допустимы только в core/platform, не в features/UI.

| Платформа | Действие пользователя | Что остаётся проверить |
|---|---|---|
| Web и установленная Web/PWA | После успешного сохранения — одна перезагрузка текущего адреса, включая path/query/fragment. При прежнем коде после reload оставить экран/повтор/инструкцию, не запускать новый reload автоматически | Реальный HTTP-кэш/bootstrap/worker, Back/refresh, несколько вкладок, восстановление draft/pending |
| Android | После сохранения — открыть принятый URL Android-выпуска; при возврате перечитать метаданные/политику, не считать ссылку установкой | Реальное открытие/установка, SDK/магазинный или APK канал, восстановление |
| iOS | Та же логика с принятым URL iOS-выпуска; нет URL — нет выдуманной кнопки магазина | Изменения общего кода допустимы, runtime/сборка по действующему запрету отложены |

Нет программного «очистить все данные браузера», удаления токена/черновика, регистрации автоповтора заказа или бесконечных reload. Стандартный `Location.reload()` не гарантирует обход кэша; параметр forceGet нестандартный, контракт на него не опирается ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Location/reload)).

Перед действием обновления оркестрация уровня app должна:

1. Временно закрыть новые изменения/отправки, дождаться ранее поставленных сохранений черновика **текущего владельца/API/окружения**. У CartDraftStore нет готового flush, поэтому до реализации проверить очередь в контроллере и добавить проверяемое ожидание фактического сохранения, а не Future-заглушку.
2. Если отправка заказа сейчас выполняется или восстановление попытки ещё идёт, отложить действие обновления; не прерывать запрос программной навигацией. Полученную позже новую minimum-policy применить к новым операциям, сохраняя завершение/результат уже начатой.
3. Если исход отправки неизвестен, сохранить прежние body/submissionId и предварительные суммы в CartSubmissionStore с прежней областью owner/API/environment, дождаться записи. После обновления сначала восстановить/выяснить результат прежней попытки; не запускать повторный POST только из-за refresh.
4. При ошибке записи показать причину и остаться на месте. Не перезагружать и не открывать выпуск, не считать снимок сохранённым.
5. Применить проверенное действие распространения. При холодном required существующие draft/pending лишь сохраняются в хранилище; проверки заказа откладываются до совместимой версии. Общая инфраструктура не импортирует features: оркестрация app получает необходимые зависимости сохранения.

Миграции формата draft/pending должны читать текущие записи v1; если это станет невозможно, нужен отдельный план миграции до повышения минимума. Актуальные бизнес-данные по-прежнему загружаются из API; локальный черновик не даёт права офлайн-заказа. Межвкладочное редактирование/блокировка записи не считаются решёнными существующими очередями — отдельный критерий живой проверки.

## 6. Выпуск и Web-инфраструктура

- В FL-06-20o добавлены параметр URL для всех клиентов/тестовых фикстур и чистые модель/сравнение → Repository через общий публичный транспорт → ручной Riverpod Controller. В FL-06-20p app вызывает проверку один раз при старте; затем только явные повторы. Web URL ограничен HTTPS-корнем origin конфигурации; native allowlist пуст до принятия конкретных ссылок продукта, поэтому production Repository допускает для native только null. Startup gate и общий UI выполнены FL-06-20p. Действие обновления остаётся отдельным шагом после принятия ADR-9 и проверки сохранности.
- Расширение version.json потребует правки build/deploy/rollback проверок: существующие сценарии сейчас сравнивают JSON целиком с парой version/build. Сверять идентификацию по этой паре, policy валидировать отдельно; нельзя просто выключить проверки.
- Версия, policy и Web-артефакты публикуются одним проверенным выпуском; откат возвращает и старые файлы, и прежнюю policy. При сохранении legacy-файла без policy новый клиент получает unknown, не ложный required. Мобильные скрипты получают тот же источник среды; обновление их параметров не означает сборку/публикацию магазинов.
- Минимум повышается после доступности принятых compatible-выпусков для всех затронутых активных клиентов и проверки сохранности/миграций. Сам факт нового Web build не повышает минимум автоматически.
- Для Web должны подтверждаться свежие index.html/bootstrap/main.dart.js/worker и отсутствие неконтролируемой навигации всех вкладок. Имеющегося `no-cache` только для version.json недостаточно для заявления о новом исполняемом коде после reload. Нужны безопасный bootstrap/worker и при необходимости точечные cache headers на **Flutter vhost**; изменения Caddy — отдельная разрешённая инфраструктурная подзадача, не часть этой документации/автоматической выкладки.
- [Flutter initialization](https://docs.flutter.dev/platform-integration/web/initialization) допускает собственный bootstrap. Конкретное решение выбирается по фактическому SDK и проверяется на уже установленном прежнем worker: новый bootstrap сам по себе не отменяет события активации старой вкладки. Не обещать сохранность при переходе со старых сборок до живой проверки миграции.
- Установка/статический кэш PWA из NFR-PWA-2 остаются отдельной задачей. Отключение автоматической навигации для W07 не считать доказательством установки PWA или выполнения требований статического кэша.

## 7. Критерии будущей реализации и решения владельца

## 8. Фактическая интеграция FL-06-20p

- Общий app-level экран до router: checking не читает сессию/бизнес-модули; required показывает текущую/минимальную версии, повтор, поддержку/политику без создания бизнес-router. Неизвестный минимум даёт явное продолжение с повторной проверкой актуального состояния в действии (старый callback не обходит начатый retry/required); compatible открывает прежний адрес и обычную сессию. Нет подмены версии сервера/автоматического reload.
- После первого допуска router и дерево бизнес-экранов сохраняются при повторе; Offstage/ExcludeFocus/TickerMode закрывают ввод, фокус и доступность. onEnter/onExit защищают новые переходы и pop/Back. Ранее начатые операции сохраняют возможность завершить обработку ответа; это не утверждение об остановке всех фоновых запросов и не серверная защита API.
- available — неблокирующая подсказка с «Позже»; unknown после явного продолжения — предупреждение с повтором/закрытием. Ключ бизнес-дерева сохраняет форму при появлении/закрытии предупреждения.
- Поддержка/политика в gate доступны локально, без бизнес-навигации и сетевых операций. Действие обновления и кнопка запуска выпуска пока не реализованы: требуется отдельная ADR-9/сохранность/worker и приёмка.
- Analyze, 325 тестов (10 новых widget-сценариев); Web +10 собран локально, test +8. Выбор native-каналов в VM-тестах синтетический и не является iOS/Android runtime-проверкой. APK/AAB +4 не пересобраны, iOS не запускалась.

## Уточнение Android от 02.10.2026 (FL-UX-32)
При завершённой ошибке проверки (unknown с failure, без checking) Android автоматически продолжает работу и не показывает технический баннер unknown. Состояние ошибки не заменяется успешной проверкой. Подтверждённое required по-прежнему блокирует работу, в том числе при неудаче повторной проверки; available сохранено. Web/iOS сохраняют прежнее явное продолжение и баннер. Исходная проверка и её deadline сохранены. Недоступный prod endpoint следует настроить отдельно; это изменение не публикует policy.
