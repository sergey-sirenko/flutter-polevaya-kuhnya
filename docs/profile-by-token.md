# Профиль по токену (`POST V1/User/login`)

**Версия:** 1.0 от 27.09.2026 · задача [FL-02-11](tasks/FL-02-11.md) · API-4 / NFR-SEC-2.

Канонический серверный обработчик: Zak `ОбменHTTP.ШаблонUserLogin`. Клиент Flutter: `SessionRepository.verify` + `UserProfile`.

## Запрос

| Поле | Обязательно | Смысл |
|---|---|---|
| `token` | да (ветка профиля) | Сессионный токен без пароля |
| `deviceId` | да | Bare UUID устройства (как FL-01-13) |
| `orderdate` | нет | Начало периода истории `user.order` (иначе ~7 суток назад) |

Пароль в этой ветке **не** передаётся.

## Успех (HTTP 200)

`{ success: true, message, token, user }`.

- **token:** на парольном входе — новый GUID; на обновлении по токену — **тот же** переданный токен (FL-02-11). Клиент сохраняет прежний, если поле пустое.
- **user:** профиль + условия + история (см. ниже).

### Поля `user`

| Поле | Смысл |
|---|---|
| `name`, `email`, `phone`, `login`, `employee` | Профиль (email/phone/employee — от сотрудника, если задан) |
| `DiscountPercentage`, `DiscountClient`, `DiscountPromotion` | Условия скидки / дотации |
| `Limit`, `LimitPeriod` | Лимит суммы и период |
| `MinimumOrderAmount`, `MinimumPaymentAmount` | Минимумы (MPA также с кириллическим ключом на сайте — см. pricing-spec) |
| `order` | Массив дней истории заказов |

Элемент `order[]`: `date`, `weekType`, `changes`, `status`, `dishes[]`, `discount`, `sum`.  
Элемент `dishes[]`: `dish`, `name`, `menunumber`, `quantity`, `sum`, `DiscountPercentage`, `DiscountClient`.

## Ошибки

Целевая форма и HTTP — [контракт ошибок v1.0](../../Zak/docs/api-errors.md) (реализация BSL в исходниках FL-02-17b; в ИБ может быть ещё не загружена).

| Ситуация | HTTP | `code` | Текст (как в BSL, поле `error`/`message`) |
|---|---|---|---|
| Нет / невалидный / просроченный токен (>24 ч) | 401 | `invalid_session` | «Неверный или устарел токен авторизации…» |
| Устройство без доступа / ограничено | 403 | `access_denied` | «Нет доступа» или «Ограничен, дата …» |
| Неверное устройство или сотрудник сеанса | 403 | `device_mismatch` | «Неверное устройство…» / «Сотрудник не соответствует…» |
| Нет `deviceId` | 400 | `invalid_request` | «Отсутствует поле deviceId» |
| Неверный пароль / неизвестный логин | 400 | `invalid_credentials` | соответствующие тексты |

Клиент после FL-02-17c: HTTP 401 и коды `invalid_session`/`invalid_token`/`device_mismatch`/`session_unbound` очищают токен (`requiresReauth`); `access_denied` и старый HTTP 400 без кода при восстановлении оставляют токен (`unavailable`). Живая приёмка — FL-02-17f.

## Проверка доступа (FL-02-11)

После валидации токена сервер вызывает `ИдКлиентаДоступРазрешен(Пользователь, deviceId)` — так же, как при парольном входе. Ранее на token-ветке `deviceId` только присутствовал в теле и **не** сверялся с привязкой.

## Совместимость

- Старый сайт шлёт `{token, deviceId}` — при разрешённой привязке поведение сохраняется; при чужом/запрещённом устройстве refresh теперь получит отказ (ожидаемо).
- Flutter: профиль в памяти после `verify`, **не** в Secure Storage / SharedPreferences. После FL-03-01 `UserProfile` хранит неизменяемый снимок ответа; неверные элементы истории вызывают ошибку формата вместо молчаливого пропуска.

## Клиентское изменение дня (FL-10-12)

Поле `user.order[].changes`: серверные строки «Открыт»/«Закрыт»; Flutter также принимает boolean. Неизвестное значение не разрешает изменение. Кнопка дня требует успешного чтения menudates и открытого существующего заказа; день без заказа использует menudates. Подготовка заново читает профиль по токену, сравнивая basketstate до/после; пересоздание сессии и изменение формата API не требуются. История остаётся источником состава, квитанция отправки — отдельным подтверждением результата.
