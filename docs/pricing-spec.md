## 1. Словарь условий клиента (FL-02-01)

Условия приходят в объекте `user` ответа login / обновления профиля. Ниже — смысл каждого параметра для Flutter. Порядок вычислений и полная нормализация — в следующих разделах.

### 1.1. Сводная таблица

| Бизнес-имя (ТЗ) | HTTP-поле `user` | Реквизиты Zak (источник) | Единица / тип | Краткий смысл |
|---|---|---|---|---|
| Процентная скидка | `DiscountPercentage` | `ПроцентСкидки` пользователя | % (0…100) | Доля, на которую уменьшается сумма блюд до применения дневной «без оплаты» |
| Дневная сумма без оплаты / дотация | `DiscountClient` | `СуммаСкидкиДень` (сотрудник, иначе пользователь) | ₽, сумма за **день** | Фиксированная сумма, которая списывается с итога дня «без оплаты»; UI сайта: «Без оплаты (N ₽)» |
| Признак дотации (акции) | `DiscountPromotion` | `СуммаСкидкиЭтоДотация` пользователя → `1` / `0` | флаг | `1` = режим **дотации**: действуют минимальная оплата и снижение порога минимального заказа; `0` = обычная дневная «без оплаты» без этих правил |
| Минимальная оплата сотрудника | `MinimumPaymentAmount` (и вариант с кириллической «А», см. FL-02-02) | `МинимальнаяСуммаОплаты` (сотрудник > 0, иначе пользователь) | ₽ | Нижняя граница того, что сотрудник всё же платит в день при режиме дотации |
| Минимальный заказ | `MinimumOrderAmount` | `МинимальнаяСуммаЗаказа` (сотрудник > 0, иначе пользователь) | ₽ за **день** с блюдами | Порог итога дня после скидок; ниже — день считается нарушением минимума |
| Лимит суммы | `Limit` | `ОграничениеПоСумме` (сотрудник > 0, иначе пользователь) | ₽ | Верхний предел трат за выбранный период; `≤ 0` / отсутствует → лимит не действует |
| Период лимита | `LimitPeriod` | `ПериодЛимита` (`Строка(Перечисление)`); если лимит > 0 и период пуст → «День» | строка | С чем сравнивать корзину: день или неделя (см. ниже) |

### 1.2. Процентная скидка (`DiscountPercentage`)

- **Смысл:** процентная скидка на сумму блюд (до дневной «без оплаты»).
- **Источник:** настройка пользователя `ПроцентСкидки` → поле login `DiscountPercentage`.
- **Клиентский сайт:** на строке и дне считает `Math.round(base * pct / 100)`; значение > 100 обрезает до 100; ≤ 0 → скидки нет.
- **Сервер:** при записи заказа пересчитывает процент из настроек пользователя; клиентский процент не источник истины.
- **Не путать с** `DiscountClient` (денежная «без оплаты», не процент).

### 1.3. Дневная «без оплаты» / дотация (`DiscountClient`)

- **Смысл:** фиксированная сумма в рублях на **календарный день** заказа, уменьшающая сумму к оплате. На сайте подпись «Без оплаты».
- **Источник:** `СуммаСкидкиДень` текущего **сотрудника**, если он задан; иначе пользователя.
- **Два режима** (зависят от `DiscountPromotion`):
  - **Обычная дневная сумма** (`DiscountPromotion ≠ 1`): доступная «без оплаты» за день равна нормализованному `DiscountClient` (без усечения по минимальной оплате).
  - **Дотация** (`DiscountPromotion = 1`): эффективная «без оплаты» ограничивается так, чтобы после процентной скидки сотрудник заплатил не меньше `MinimumPaymentAmount` (если MPA > 0). Если сумма дня после % ≤ MPA, эффективная дотация за день = 0.
- **Распределение по строкам (сайт, предварительный показ):** остаток дневной суммы последовательно уменьшает строки дня; на сервер в `Orders/basket` уходит рассчитанный `DiscountClient` **по строке**. Сервер для сотрудника пишет это в `БезОплатыДень`.
- **Не путать с** процентной скидкой и с итогом скидки в истории заказа (`discount` / суммы строк).

### 1.4. Признак дотации (`DiscountPromotion`)

- **Смысл:** включает ли организация режим **дотации** для денежной дневной суммы.
- **Источник:** реквизит пользователя `СуммаСкидкиЭтоДотация` → в HTTP `1` или `0`.
- **Клиентский сайт:** `Number(DiscountPromotion) === 1` → `isDiscountPromotion: true`.
- **Эффекты при `true` (по JS сайта):**
  1. Учёт `MinimumPaymentAmount` при расчёте эффективной дотации за день.
  2. Эффективный минимум заказа = `max(0, MinimumOrderAmount − DiscountClient)` (порог снижается на полную дневную дотацию профиля, не на уже усечённую по дню).
- При `false` оба эффекта отключены: минимум заказа = `MinimumOrderAmount` без вычитания; MPA на дотацию не влияет.

### 1.5. Минимальная оплата (`MinimumPaymentAmount`)

- **Смысл:** сколько сотрудник **обязан оплатить** минимум за день при режиме дотации (после процентной скидки, до/с учётом дотации — детали порядка в FL-02-03).
- **Источник:** `МинимальнаяСуммаОплаты` сотрудника, если > 0; иначе пользователя. В форме пользователя Zak поле связано с флагом «сумма скидки — это дотация».
- **HTTP:** `MinimumPaymentAmount`; на сайте также встречается ключ с **кириллической «А»** (`MinimumPaymentАmount`) — нормализация в FL-02-02.
- **Когда не действует:** `DiscountPromotion ≠ 1` или значение ≤ 0 → сайт не усекает дневную «без оплаты» по MPA.
- **Не путать с** минимальной суммой **заказа** (`MinimumOrderAmount`).

### 1.6. Минимальный заказ (`MinimumOrderAmount`)

- **Смысл:** минимальный итог **дня** (после клиентских скидок в предварительном расчёте), при котором день с блюдами допустим.
- **Источник:** `МинимальнаяСуммаЗаказа` сотрудника, если > 0; иначе пользователя.
- **Проверка на сайте:** дни с пустой корзиной не проверяются; сравнивается `finalTotal` дня с эффективным минимумом (см. 1.4).
- **Сервер:** `НедостаточнаяСуммаЗаказа` сравнивает сумму после скидок с минимумом и может отказать в записи (точные сообщения — runtime).
- **≤ 0:** порог не применяется.

### 1.7. Лимит (`Limit`) и период (`LimitPeriod`)

- **Смысл:** верхняя граница суммы заказов клиента за период (день или неделя), чтобы не превысить договорённый бюджет.
- **Источник суммы:** `ОграничениеПоСумме` сотрудника, если > 0; иначе пользователя.  
  **Источник периода:** у сотрудника свой `ПериодЛимита`, если заполнен и взят его лимит; иначе период пользователя. Если лимит > 0, а период пуст → сервер подставляет **День**.
- **HTTP:** `Limit` (число), `LimitPeriod` (`Строка` перечисления, на клиенте сравнивается без регистра).
- **Клиентский сайт (`LIMIT_PERIOD`):** `'день'` | `'неделя'`. При периоде «неделя» с лимитом сравнивается итог **недели**; иначе — итог **текущего дня** (после скидок). Остаток = `Limit − comparedTotal` (округление на сайте через `Math.round`).
- **≤ 0 / нечисловой Limit:** лимит в UI не показывается и не ограничивает.
- **Сервер:** при записи заказа отдельно проверяет превышение с учётом уже проведённых заказов периода (детализация — FL-02-04); клиентский остаток предварительный.

## 2. Нормализация значений (FL-02-02)

Цель раздела: единые правила приведения сырых значений профиля/`user` к числам и флагам **до** расчёта. Эталон — функции `normalize*` / чтение полей в `js/state.js` (и отображение в `profileManager.js`). Порядок применения скидок — FL-02-03.

### 2.1. Общие правила разбора чисел

Для денежных полей и процента сайт использует один шаблон:

1. `parseFloat(value)` (для `Limit` в настройках лимита — `Number.parseFloat`).
2. Если результат **не** `Number.isFinite` **или** `<= 0` → нормализованное значение **`0`** (поле «выключено» / не действует).
3. Иначе — поле-специфичное ограничение (см. таблицу).

Следствия:

| Вход | Результат (для денежных / % по правилам ≤0 → 0) |
|---|---|
| `null`, `undefined`, отсутствующий ключ | `0` |
| `""`, пробельная строка (после parseFloat → NaN) | `0` |
| `"12.5"`, `12.5` | далее по правилу поля |
| `"12,5"` (запятая) | `parseFloat` в JS даёт `12` — **известное ограничение сайта**; для Flutter зафиксировать явно (рекомендация ниже) |
| `"abc"`, `NaN`, `Infinity` | `0` |
| `0`, отрицательные числа | `0` |

**Рекомендация для Flutter (не меняет текущий сайт):** принимать и `.`, и `,` как десятичный разделитель при разборе строк, затем применять те же пороги `<= 0` → 0. Расхождение со старым сайтом на вводе с запятой выделить при согласовании (FL-02-06).

### 2.2. Правила по полям профиля

| Поле | Функция сайта | После `parseFloat` / конечное значение | Округление / клип |
|---|---|---|---|
| `DiscountPercentage` | `normalizeDiscountPercentage` | `<= 0` или не число → `0`; иначе `min(value, 100)` | **без** `Math.round` (дробный % допускается до клипа) |
| `DiscountClient` | `normalizeDiscountClient` | `<= 0` или не число → `0` | `Math.round` |
| `MinimumOrderAmount` | `normalizeMinimumOrderAmount` | `<= 0` или не число → `0` | `Math.round` |
| `MinimumPaymentAmount` | `normalizeMinimumPaymentAmount` | `<= 0` или не число → `0` | `Math.round` |
| `Limit` | `Number.parseFloat` в `getUserLimitSettings` / UI | если не finite или `<= 0` → лимит **не активен** (`null` настроек / скрытие строки) | для отображения остатка корзины используется `Math.round` отдельно (FL-02-03) |
| `LimitPeriod` | `normalizeUserLimitPeriod` | `String(value ?? '').trim().toLowerCase()` | сравнение с константами `LIMIT_PERIOD.DAY === 'день'`, `WEEK === 'неделя'`; иное / пустое при активном лимите на сайте в сравнении с лимитом ведёт себя как **не неделя** (итог **дня**) — см. §2.4 |
| `DiscountPromotion` | `Number(value) === 1` | Режим дотации только если после `Number(...)` результат **строго равен `1`** | `"1"` и `1` → дотация; `0`, `"0"`, `""`, `null` → нет; булево `true` в JS тоже даёт `Number(true)===1` (краевой случай сайта) |

Наблюдение сайта (комментарий в коде): с 1С иногда приходит ключ с **кириллической «А»** вместо латинской A в слове Amount.

| Ключ | Код символа «A/А» | Примечание |
|---|---|---|
| `MinimumPaymentAmount` | U+0041 LATIN CAPITAL A | канонический |
| `MinimumPaymentАmount` | U+0410 CYRILLIC CAPITAL A | `MinimumPayment` + `\u0410` + `mount` |

Алгоритм чтения сырого значения (`getUserMinimumPaymentAmountValue`):

1. Если `userData` отсутствует → `undefined`.
2. Если `userData.MinimumPaymentAmount != null` и не `''` → взять **латинский** ключ (приоритет).
3. Иначе если значение по кириллическому ключу `!= null` и не `''` → взять его.
4. Иначе → `undefined` (далее нормализация даст `0`).

После входа / обновления профиля `normalizeUserDataFromServer` **копирует** найденное сырое значение в канонический ключ `user.MinimumPaymentAmount`, не удаляя кириллический (если оба были).

Для Flutter: при разборе JSON профиля сначала читать латинский ключ, иначе кириллический; внутри модели хранить одно поле.

### 2.4. Нормализация `LimitPeriod`

1. Привести к строке: `String(limitPeriod ?? '').trim().toLowerCase()`.
2. Активный недельный режим только если результат **строго равен** `'неделя'` (`LIMIT_PERIOD.WEEK`).
3. Любое другое значение (включая `'день'`, пустую строку, `'месяц'`, латиницу `week`) при сравнении суммы с лимитом на сайте даёт ветку **дня** (`getCartTotalsForUserLimit`).
4. Подпись в UI: при неделе — «за неделю», иначе — «за день».
5. Отображение периода в профиле показывает **сырую** строку `LimitPeriod` с сервера (без lower-case), если лимит активен.

**Открыто:** поведение сервера для периода «Месяц» и иных значений перечисления — не подтверждено runtime (см. §1.9). Клиент Flutter до FL-02-04/05 должен трактовать неизвестный период как день **в согласии с сайтом**, либо явно отложить поддержку.

### 2.5. Нормализация цены и количества строки (для последующего расчёта)

В `getLineTotalsWithDiscount` сайт:

- цена: `Number(price)` → если не finite → `0`;
- количество: `Number(quantity)` → если не finite → `0`.

Пустая/битая строка меню даёт нулевую базу строки. Детальный порядок скидок — FL-02-03.

### 2.6. Целевое поведение Flutter-модуля `pricing`

До реализации Dart зафиксировать контракт нормализации:

1. Все условия клиента прогонять через функции, эквивалентные таблице §2.2.
2. MPA читать с приоритетом латинского ключа (§2.3).
3. `DiscountPromotion` считать истинным только если после приведения к числу значение **строго равно 1** (как `Number(x) === 1` на сайте).
4. Неактивные суммы/процент/`Limit` — ноль / отсутствие лимита, а не `null` в арифметике (кроме явного «лимит выключен»).
5. Разбор `"12,5"` — улучшить относительно сайта (запятая → точка) и отметить в FL-02-06 как намеченное отличие, если заказчик согласится.

### 2.7. Вне объёма FL-02-02

- Последовательность % → дотация → округление по строкам — FL-02-03.
- Учёт уже сохранённых заказов в лимите на сервере — FL-02-04.
- Числовые примеры — FL-02-05.

## 3. Порядок вычислений и округление (FL-02-03)

Эталон — `getLineTotalsWithDiscount`, `calculateDayTotalAfterPercentage`, `resolveEffectiveDiscountClientForDay`, `getDayLinesWithDiscounts`, `calculateDayTotalsWithDiscount`, `calculateWeekTotalsWithDiscount`, `getCartTotalsForUserLimit` в `js/state.js`. Клиентский расчёт — только предварительный показ; сервер Zak пересчитывает при записи заказа ([FL-00-12](tasks/FL-00-12.md), §1 preamble).

### 3.1. Уровень строки (одно блюдо в дне)

Вход: `price`, `quantity`, `discountPercentage`, `discountClientAvailable` (остаток дневной «без оплаты», доступный **на момент этой строки** — см. §3.3).

Шаги `getLineTotalsWithDiscount`, **в этом порядке**:

1. `normalizedPrice = Number(price)` (не finite → `0`); `normalizedQuantity = Number(quantity)` (не finite → `0`).
2. `baseTotal = max(0, round(normalizedPrice × normalizedQuantity))` — **округление суммы строки уже здесь**, до применения любой скидки.
3. `discountAmount = calculateDiscountAmount(baseTotal, discountPercentage)` = `round(baseTotal × normalizedPercent / 100)`, где `normalizedPercent` — по §2.2 (клип 0…100); при `baseTotal ≤ 0` или проценте `≤ 0` → `0`.
4. `totalAfterPercentage = max(0, round(baseTotal − discountAmount))`.
5. `normalizedDiscountClient = normalizeDiscountClient(discountClientAvailable)` (по §2.2, уже целое ≥ 0).
6. `discountClientAmount = min(totalAfterPercentage, normalizedDiscountClient)` — «без оплаты» по строке не может превысить остаток после процентной скидки **и** не может превысить переданный остаток дневного лимита дотации/скидки.
7. `finalTotal = max(0, round(totalAfterPercentage − discountClientAmount))`.

Результат строки: `{baseTotal, discountAmount, totalAfterPercentage, discountClientAmount, finalTotal}`. **Порядок скидок: сначала процентная, затем фиксированная «без оплаты» — от суммы, уже уменьшенной процентом.**

### 3.2. Эффективная дневная сумма «без оплаты» (до распределения по строкам)

`resolveEffectiveDiscountClientForDay(weekType, dayNumber, discountPercentage, discountClient, discountClientOptions)`:

1. `normalizedDiscountClient = normalizeDiscountClient(discountClient)`; если `≤ 0` → эффективная сумма дня = `0` (шаги 2–4 не выполняются).
2. Если `isDiscountPromotion` **ложно** ИЛИ `minimumPaymentAmount ≤ 0` → эффективная сумма дня = `normalizedDiscountClient` (весь профильный лимит доступен на день, без дальнейшего усечения).
3. Иначе (режим дотации с MPA > 0):
   - `dayTotalAfterPercentage = calculateDayTotalAfterPercentage(weekType, dayNumber, discountPercentage)` — сумма **всех строк дня** после процентной скидки, **без** учёта дотации (шаги 3.1 п.1–4 по каждой строке, просуммированные и округлённые `round(Σ totalAfterPercentage)`).
   - Если `dayTotalAfterPercentage ≤ minimumPaymentAmount` → эффективная сумма дня = `0` (дотация не положена: и так меньше/равно минимальной оплате).
   - Иначе → эффективная сумма дня = `min(normalizedDiscountClient, max(0, round(dayTotalAfterPercentage − minimumPaymentAmount)))`.

**Смысл:** при дотации сотрудник должен заплатить минимум `MinimumPaymentAmount`; дотация «съедает» только то, что выше этого порога, и не больше профильного лимита за день.

### 3.3. Распределение дневной суммы «без оплаты» по строкам

`getDayLinesWithDiscounts`:

1. Взять `remainingDiscountClient` = результат §3.2 (эффективная сумма на весь день).
2. Отсортировать блюда дня по порядку в меню (`menuOrder`, иначе `Number.MAX_SAFE_INTEGER` — без порядка меню в конец).
3. Для каждой строки **по порядку**:
   - Вызвать §3.1 с `discountClientAvailable = remainingDiscountClient` (текущий остаток).
   - `remainingDiscountClient = max(0, remainingDiscountClient − totals.discountClientAmount)`.
4. Следующая строка получает **уменьшенный остаток**; «без оплаты» расходуется последовательно от первой строки меню к последней, не превышая по каждой строке её `totalAfterPercentage` (п.3.1.6).

**Важно:** это клиентский порядок распределения по строкам для предпросмотра; сервер при записи заказа пересчитывает свои строки самостоятельно (см. [FL-00-12](tasks/FL-00-12.md), `БезОплатыДень`/`СкидкаКлиентуСумма`) — согласование поштрочного округления HTTP-записи и JS не доказано (открытый пункт §1.9 п.2).

### 3.4. Итог дня

`calculateDayTotalsWithDiscount`:

1. Просуммировать по всем строкам дня (результат §3.3) отдельно `baseTotal`, `discountAmount`, `discountClientAmount`, `finalTotal`.
2. Округлить **каждую** из четырёх сумм: `round(Σ baseTotal)`, `round(Σ discountAmount)`, `round(Σ discountClientAmount)`, `round(Σ finalTotal)`.

Поскольку слагаемые уже целые (round на уровне строки), это округление в основном не меняет сумму, но формально применяется всегда — фиксируем как часть контракта (на случай дробных % без промежуточного round, см. §2.2 «без `Math.round`» для процента).

### 3.5. Итог недели

`calculateWeekTotalsWithDiscount(weekType, ...)`:

1. Для **каждой даты корзины**, относящейся к данному `weekType` (по `getWeekTypeForDate`), получить дневные итоги §3.4 для дня этой даты.
2. Просуммировать все 4 поля по дням недели.
3. Округлить каждую сумму (`round(...)`) — аналогично §3.4.

### 3.6. Сравнение с лимитом (`Limit` / `LimitPeriod`)

`getCartTotalsForUserLimit(limitPeriod, weekType, dayNumber, ...)`:

- Если нормализованный `LimitPeriod` (§2.4) строго `'неделя'` → используются итоги §3.5 (**вся неделя** `weekType`, а не только выбранный день).
- Иначе → итоги §3.4 для конкретного `dayNumber` (**один день**).
- Сравнивается `finalTotal` этих итогов с `Limit`; остаток для UI = `round(Limit − finalTotal)`, показывается только если `hasLimit` (см. §1.7 / §2.2).

Сравнение всегда идёт по **`finalTotal`** (после процентной **и** дневной «без оплаты» скидок) — не по `baseTotal`.

### 3.7. Сводная последовательность (сверху вниз)

1. Строка: цена×кол-во → round → **%-скидка** (round) → «без оплаты» по остатку строки/дня (min, затем убывающий остаток) → round.
2. День: сумма строк по каждому из 4 полей → round каждого поля.
3. Неделя (если нужна): сумма дневных итогов по `weekType` → round каждого поля.
4. Лимит: выбор день/неделя по `LimitPeriod` → сравнение `finalTotal` с `Limit`.
5. Минимальный заказ (эффективный, §1.6/1.4) сравнивается с `finalTotal` дня отдельно — вне цепочки лимита, конкретные пороги и период — FL-02-04.

### 3.8. Округление — сводка правил

| Что округляется | Функция округления | Когда |
|---|---|---|
| Сумма строки до скидок (`price × quantity`) | `Math.round`, затем `max(0, …)` | всегда |
| Сумма процентной скидки | `Math.round` | всегда, из уже округлённого `baseTotal` |
| Остаток после процента | `Math.round`, `max(0, …)` | всегда |
| Сумма «без оплаты» по строке | целое (уже из `normalizeDiscountClient`, `min` целых) | — (min двух целых) |
| Итог строки после «без оплаты» | `Math.round`, `max(0, …)` | всегда |
| Итоги дня/недели (4 поля) | `Math.round` каждого просуммированного поля | всегда, после суммирования округлённых слагаемых |
| Остаток лимита для UI | `Math.round` | при активном лимите |

**Открыто:** согласование этой последовательности и округлений с фактическим серверным HTTP-пересчётом Zak не подтверждено runtime — перенесено в реестр несоответствий и предстоящую сверку FL-02-09/FL-02-10.

## 4. Ограничения заказа (FL-02-04)

Раздел описывает **когда** заказ (или изменение корзины) считается недопустимым по минимуму и лимиту, и **как** считаются периоды. Источники: клиент — `getDaysBelowMinimumOrderAmount`, `checkLimitForQuantityChange`, `syncCartLimitSummary` (`state.js` / `eventHandlers.js` / `renderCart.js`); сервер — `НедостаточнаяСуммаЗаказа`, `ПревышенЛимитЗаказа`, вызовы в `ЗаписатьЗаказ` (HTTP) и `MAExchange` (SOAP).

### 4.1. Минимальная сумма заказа

| Аспект | Клиент (сайт, предварительный) | Сервер Zak |
|---|---|---|
| Порог | `MinimumOrderAmount` после нормализации (§2); при дотации эффективный = `max(0, min − DiscountClient)` (§1.4) | `ПолучитьМинимальнуюСуммуЗаказа()` — сотрудник > 0, иначе пользователь; **без** вычитания `DiscountClient` в коде проверки |
| Что сравнивается | `finalTotal` **каждого непустого дня** корзины (§3.4) | Пересчитанная сумма строк текущего заказа «со скидками» (см. ниже) |
| Пустой день | Не проверяется (нет позиций) | Документ с нулевым количеством может помечаться к удалению / не проводится — отдельно от минимума |
| Когда срабатывает | Перед отправкой корзины (`eventHandlers`): если есть нарушения — ошибка, отправка не идёт | `НедостаточнаяСуммаЗаказа` вызывается в **SOAP/Mob** (`MAExchange`) **после** пересчёта скидок; в HTTP-пути `ЗаписатьЗаказ` вызов **этой** функции **не найден** (статически) |
| Сообщение (сервер) | — | Шаблон: «Изменения не приняты! / Минимальная сумма заказа N руб. / Ваш заказа на сумму (сумма−минимум) руб.» (формулировка как в BSL; runtime не сверен) |

**Серверный расчёт суммы для минимума (`НедостаточнаяСуммаЗаказа`):**

- **Сотрудник задан:** по строкам `ЗаказПоСотрудникам` текущего сотрудника: доля строки состава `(Сумма − СкидкаПроцент − СкидкаСумма) / КоличествоСостава × КоличествоСотрудника`, `Окр(..., 2)`, сумма по строкам.
- **Обычный пользователь:** по `СоставЗаказа` с `Количество > 0`: `Σ (Сумма + СкидкаПроцент + СкидкаСумма)` — в коде знаки «+» к полям скидок; **семантика знаков полей скидок в документе требует runtime-сверки** (не утверждать знак без примера).
- Если порог `0` → проверка не выполняется.
- Нарушение: `СуммаЗаказаСоСкидками < МинимальнаяСуммаЗаказа`.

**Клиент vs сервер (зафиксировать как расхождение до FL-02-06):**

1. Клиент снижает порог на `DiscountClient` при `DiscountPromotion=1`; серверная функция минимума этого не делает.
2. HTTP-запись заказа на сайте, судя по статическому коду, **не** вызывает серверный минимум — полагается на клиентскую проверку; SOAP/Mob вызывает оба ограничения.

### 4.2. Лимит суммы: клиентский предпросмотр

| Аспект | Поведение сайта |
|---|---|
| Активация | `Limit > 0` после `parseFloat` (§2.2) |
| Периоды UI | Только `'день'` и `'неделя'` (§2.4). Значение `'месяц'` / иное → сравнение как **день** |
| Сравниваемая сумма | `finalTotal` текущего дня **или** всей недели `weekType` (§3.6) — **только содержимое локальной корзины**, без запроса уже сохранённых заказов |
| При добавлении/изменении кол-ва | `checkLimitForQuantityChange`: проекция итога после изменения; если `projectedTotal > Limit` → запрет изменения, сообщение с `scopeLabel` («за день»/«за неделю») |
| В корзине | `syncCartLimitSummary`: показывает лимит, период, остаток `round(Limit − comparedTotal)`; класс превышения при `remainder < 0` |

Клиент **не** учитывает уже проведённые заказы на сервере: остаток в UI — только относительно текущей корзины сессии.

### 4.3. Лимит суммы: сервер при записи

Функция `ПревышенЛимитЗаказа(ЗаказОбъект)`:

1. Берёт `ОграничениеПоСумме` и `ПериодЛимита` (сотрудник > 0 → его лимит/период; иначе пользователь; пустой период → **День**).
2. Если ограничение `≤ 0` → лимит не проверяется.
3. Иначе ветка **без сотрудника** / **с сотрудником**.

#### 4.3.1. Обычный пользователь (нет текущего сотрудника)

| Период | Сумма текущего заказа | Учёт других документов периода | Условие отказа |
|---|---|---|---|
| **День** | `ИтогПоКолонкеСумма` (в коде вычитание скидок **закомментировано**) | Не запрашиваются | `СуммаЗаказа > Ограничение` |
| **Неделя** | то же `ИтогПоКолонкеСумма` | `СУММА(ИтогПоКолонкеСумма − СкидкаПроцентСумма − СкидкаКлиентуСумма)` по **проведённым**, не удалённым заказам с `Дата` ∈ `[НачалоНедели; КонецНедели]`, **кроме** текущей ссылки | сумма (текущий + другие) `> Ограничение` |
| **Месяц** | то же | `СУММА(ИтогПоКолонкеСумма)` по проведённым за месяц (вычитание скидок в запросе **закомментировано**) | сумма `> Ограничение` |

Сообщения: «Сумма заказа за день/неделю/месяц превышена на X руб.»

#### 4.3.2. Сотрудник (задан `ТекущийСотрудник`)

1. Сумма **текущего** заказа по строкам сотрудника: `Окр((Сумма − СкидкаПроцент) / КоличествоСостава × КоличествоСотрудника, 2)` (поле `СкидкаСумма` / «без оплаты» в этой формуле **закомментировано**).
2. Для периода день / неделя / месяц задаются границы `НачалоДня…` / `НачалоНедели…` / `НачалоМесяца…`.
3. Из других **проведённых** заказов периода выбираются строки `ЗаказПоСотрудникам` этого сотрудника (кроме текущей ссылки) и сопоставляются с составом; к сумме добавляется та же пропорция по цене строки.
4. Отказ: `Цел(СуммаЗаказа) > ОграничениеПоСумме`.
5. **Наблюдение в коде:** текст сообщения при отказе для сотрудника всегда содержит формулировку «за **неделю**», даже если период день или месяц — вероятный дефект BSL; для Flutter не копировать слепо, сверить runtime (открытый пункт).

### 4.4. Где вызываются проверки при записи

| Канал | Лимит | Минимум заказа |
|---|---|---|
| HTTP `ОбменДанными.ЗаписатьЗаказ` (сайт / Flutter HTTP) | Да, после `РассчитатьСкидки` | **Вызов не найден** в теле `ЗаписатьЗаказ` (статика) |
| SOAP `MAExchange` | Да | Да (сразу после лимита) |

Порядок в SOAP: сначала лимит, затем минимум. Оба срабатывают **после** `Документы.ЗаказПокупателя.РассчитатьСкидки`.

### 4.5. Сводка периодов

| Значение | Клиент UI / предпросмотр | Сервер `ПериодыЛимитов` |
|---|---|---|
| День | Да (`'день'` или любое ≠ `'неделя'`) | Да; граница — календарный день даты заказа |
| Неделя | Да (`'неделя'`) | Да; `НачалоНедели`…`КонецНедели` даты заказа (неделя платформы 1С) |
| Месяц | **Нет** (трактуется как день) | Да; `НачалоМесяца`…`КонецМесяца` |

Неделя 1С и «неделя» UI сайта (`weekType` current/next меню) — **разные понятия**: серверный лимит завязан на календарную неделю даты **документа**, клиентский недельный предпросмотр — на сумму дней выбранного типа недели меню в корзине. Для Flutter зафиксировать оба смысла и не смешивать без явного решения (открытый пункт к FL-02-06).

### 4.6. Рекомендации для Flutter (черновик до согласования)

1. Предпросмотр: как сайт — минимум по дням корзины с эффективным порогом при дотации; лимит по `finalTotal` дня/недели меню **без** истории сервера.
2. После ответа `Orders/basket` / ошибки записи показывать **серверный** текст отказа как истину.
3. Не обещать в UI учёт уже сохранённых заказов в остатке лимита, пока нет API остатка; иначе пользователь увидит расхождение при отправке (сервер учтёт историю).
4. Период «месяц»: сервер может отказать при лимите месяца, даже если клиент сравнивал как день — явно учесть в ошибках / будущем контракте профиля.

### 4.7. Открытые пункты §4

1. Знаки полей скидок в `НедостаточнаяСуммаЗаказа` для обычного пользователя (сумма `Сумма + Скидка…`).
2. Почему для лимита дня/месяца у пользователя скидки в сравнении закомментированы, а для недели — нет.
3. Текст «за неделю» при любом периоде у сотрудника.
4. Подтвердить отсутствие серверного минимума в HTTP-записи runtime-ом.
5. Согласовать календарную неделю 1С vs неделя меню на клиенте.

| M-2 | день: блюдо 250; минимум = 200 | **250** ≥ **200** → ок | выше минимума |

| M-0 | день без позиций; минимум = 200 | проверка **не выполняется** | пустой день (§4.1) |

### 5.6. `Limit` / `LimitPeriod` (клиентский предпросмотр)

| ID | Вход | Ожидание | Смысл |
|---|---|---|---|
| L-1 | день итог **510**; `Limit` = 500; период «день» (или не «неделя») | **510 > 500** → превышение; остаток UI `round(500−510)` = **−10** | лимит дня |
| L-2 | день1 итог 200, день2 той же `weekType` итог 200; `Limit` = 350; период «неделя» | неделя итог **400 > 350** → превышение | лимит недели по сумме дней меню |
| L-3 | день итог 300; `Limit` = 500; период «день» | остаток **200**; изменение ок, пока проекция ≤ 500 | запас лимита |
| L-4 | день итог 300; `Limit` = 500; период **«месяц»** (или «Месяц») | клиент сравнивает как **день** (§2.4 / §4.2); сервер мог бы учесть месяц + историю (§4.3) | расхождение клиент/сервер |

**Сценарий истории (только описание, без чисел 1С):** корзина с `finalTotal` 200 при `Limit` 500 и периоде «неделя» на клиенте «в пределах»; на сервере уже есть проведённые заказы той же календарной недели на 400 → `ПревышенЛимитЗаказа` может отказать. Для сверки нужны обезличенные документы (FL-02-10 / runtime).
