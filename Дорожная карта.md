## 1. Цель, границы и текущее положение

### 1.1. Конечный результат

Единая кодовая база Flutter обеспечивает:

- публичный сайт и оформление заказов в браузере;
- устанавливаемую PWA;
- Android-приложение для Google Play, RuStore и прямой установки APK;
- iOS-приложение для App Store;
- работу с существующим сервером 1С;
- одинаковые бизнес-сценарии на всех поддерживаемых платформах.

Публичные страницы также создаются на Flutter. Небольшая HTML-оболочка используется для загрузки приложения, метаданных и резервных контактов.

Выпуск поэтапный: сначала тестирование и приёмка Web и Android, затем завершение публикаций в магазинах. При этом iOS остаётся обязательной платформой: совместимость проверяется с начала разработки, а известные ошибки общего бизнес-сценария на iOS не считаются допустимыми для завершённой версии 1.0.

Онлайн-оплата, push, биометрия, геолокация, камера, NFC, контакты, календарь, офлайн-синхронизация, native deep links и отдельные настольные приложения в версию 1.0 не входят. Полный перечень ограничений — раздел 3 ТЗ.

### 1.2. Как используется NewProject

Изучены README, архитектура и правила [NewProject](https://github.com/sergey-sirenko/NewProject). Сейчас это набор архитектурных документов: готового Flutter-каркаса и реализованного модуля Customers ещё нет. Пример используется для организации проекта, а каркас создаётся для «Полевой кухни».

Сохраняются понятная структура модулей, Riverpod, единая маршрутизация и последовательность Model → Repository → Controller → UI. Сервер, авторизация, платформы, локальный черновик, тестирование расчётов и остальные особенности определяются нашим ТЗ. Изученная ревизия и таблица отличий — в [справке](docs/newproject-reference.md).

### 1.3. Что уже изучено

Предварительным просмотром документов и клиентских исходников установлено:

- на старте в каталоге Flutter находилось только ТЗ; приложение ещё не создано;
- сайт содержит обновление профиля по токену через User/login и передаёт deviceId;
- история используется из user.order;
- отправка корзины включает разрешённые дни с пустыми списками блюд;
- поддерживается поле минимальной оплаты с латинской и кириллической «А»;
- регистрация сотрудника использует выданные реквизиты организации;
- существующий service worker называется service-worker.js;
- в сайте есть пользовательские изменения, которые нельзя смешивать с новой разработкой.

Это предварительное исследование, а не приёмка серверных функций. Работа 1С, восстановление пароля, удаление аккаунта, реальные ответы API и сборки Flutter ещё не проверялись. Источники наблюдений должны быть уточнены в FL-00-05–13.

Карточка создаётся при начале задачи. Не требуется заранее создавать сотню пустых файлов. Если карточки нет, задача не начата. Фактическое состояние задачи хранится только в её карточке; дорожная карта задаёт содержание, а PROJECT_STATE содержит ссылки.

Для межпроектной координации используется [HLEBSOL-FLUTTER](../docs/tasks/HLEBSOL-FLUTTER.md). Там фиксируются версии связанных репозиториев и готовность серверного и клиентского выпуска. Детали Flutter остаются в карточках Flutter.

### 2.2. Идентификаторы задач

Формат: FL-ЭТАП-НОМЕР, например FL-05-07.

- ID после начала работы не меняется.
- Новая задача получает новый номер.
- Отменённая задача остаётся в истории с причиной.
- При разделении задачи создаются подзадачи a, b, c.
- Каждая подзадача имеет самостоятельный проверяемый результат.

### 2.3. Состояние задачи

| Аспект | Возможные значения |
|---|---|
| Работа | Не начата / выполняется / приостановлена / заблокирована / завершена / отменена |
| Реализация | Не выполнена / частично / выполнена |
| Проверка | Не проверено / частично / прошло / есть ошибки |
| Выпуск | Не требуется / не опубликовано / тестовый контур / рабочий контур |

Написанный код не означает, что задача проверена. Сборка не означает приёмку пользователем. Публикация Web не означает публикацию Android или iOS. Для каждого результата сохраняются дата, версия кода и способ проверки.

### 2.4. Шаблон карточки

Рабочий шаблон — [docs/tasks/_template.md](docs/tasks/_template.md). Он содержит назначение, входные условия, шаги, критерии готовности, четыре аспекта состояния, выполненное, проверки, препятствия, точку остановки, версии и журнал.

### 2.5. Обновление состояния

После каждого законченного смыслового шага:

1. Обновить карточку задачи и результат проверки.
2. Указать оставшуюся работу и конкретное следующее действие.
3. При смене задачи обновить PROJECT_STATE.md.
4. При архитектурном решении обновить ADR.
5. При изменении контракта отметить затронутые задачи и повторные проверки.

После завершения каждой подзадачи обязательно остановиться: сообщить результат, проверки, ограничения и конкретные дальнейшие действия. Следующую подзадачу начинать только после нового подтверждения пользователя. Правило действует для разработки, документов и инфраструктуры; одобрение всей дорожной карты его не отменяет.

До выполнения следующей подзадачи сообщить её сложность по шкале 1–10, трудоёмкость (низкая / средняя / высокая и предварительная доля трудозатрат всего этапа в процентах) и предложить категорию LLM (лёгкая / средняя / сложная) с кратким основанием. Включать это в итог после текущей подзадачи и сверять при возобновлении; порядок оценки задан в [AGENTS.md](AGENTS.md).

## 12. Общие правила проверки

### 12.1. Для задачи с кодом

- Проверить требования и контракт, diff и сохранность пользовательских изменений.
- Выполнить анализ Flutter и предусмотренные тесты.
- Проверить изменённый сценарий на релевантных платформах.
- Записать версию кода, результаты, непроверенное и причины.
- Подставные ответы не заменяют интеграцию с 1С.

Для документации проверяются содержание, ссылки, зависимости и противоречия; приложения и кодовые тесты не требуются. Действующие ограничения запусков и контуров сохраняются до изменения пользователем.

### 12.2. Обязательный набор приёмки

| Область | Сценарии |
|---|---|
| Авторизация | Верный/неверный пароль, истёкший токен, перезапуск, выход, смена пользователя |
| Регистрация | Успех, неверный/истёкший код, повтор, ограничения, отмена, запоздавший ответ |
| Профиль | Обновление по токену, смена email, удаление |
| Меню | Пустое, ошибка JSON, недоступные даты, нет изображения, смена недели |
| Расчёт | Все примеры, округление, скидка с дотацией, лимиты, минимумы |
| Корзина | Несколько дней, пустые дни, черновик, новое меню, смена аккаунта |
| Отправка | Успех, отказ, двойное нажатие, таймаут, потеря ответа, разные суммы |
| История | Пустая, обновление после заказа, повтор без части блюд |
| Интерфейс | 360–1920, границы 600/1024, клавиатура, Назад, прокрутка, resize |
| PWA | Установка, запуск, обновление, старый worker |
| Публикация | Сборка, подпись, установка, обновления, активная версия |
| Переход | Runtime-данные, резервный адрес, откат, отсутствие циклов |

Перед выпуском полный сценарий проверяется на Chrome/Windows, Safari/macOS, Chrome/Android, Safari/iOS, Android-приложении и iOS-приложении. Матрица поддержки также включает Edge, Яндекс Браузер и Firefox согласно ТЗ.

### 12.3. Производительность

- HTML-загрузка менее 1 секунды.
- Первый доступ к главной Web менее 4 секунд.
- Повторный доступ менее 1,5 секунды.
- Меню приложения менее 2 секунд при работающей сети.

Для замера записать устройство, ОС, браузер, сеть, кэш и сборку. Без них результат невоспроизводим.

## 13. Как выполняется работа между остановками

### 13.1. Начало сессии

1. Прочитать инструкции, PROJECT_STATE и карточку текущей задачи.
2. Проверить Git и незавершённые изменения.
3. Сверить файлы с точкой остановки.
4. Проверить изменения контрактов и зависимостей.
5. Продолжить с конкретного следующего действия.

После аварийного обрыва сначала восстановить фактическое состояние по diff, файлам и проверкам. Последняя запись может не отражать все изменения.

### 13.2. Работа над задачей

1. Выбрать одну основную задачу.
2. Зафиксировать входные условия и критерии готовности.
3. Разбить её на шаги в карточке.
4. Выполнить минимальную законченную часть.
5. Проверить её и сохранить точку продолжения.
6. Если закончена текущая подзадача, сообщить пользователю результат и дальнейшие действия, завершить ответ и ждать подтверждения. Внутренние шаги одной подзадачи выполнять до её проверяемого результата.

Новая существенная работа получает ID или явно добавляется в карточку. Зависимости не остаются только в переписке.

### 13.3. Остановка

Записать завершённое, изменённые файлы, незакоммиченные изменения, проверки, ошибки, запущенные процессы, внешние зависимости и одно конкретное следующее действие.

Остановка после подзадачи обязательна, даже если работа выполнена успешно и препятствий нет. Автоматически переходить к следующей нельзя.

Пример:

> FL-05-09: сериализация непустых дней реализована и проверена. Осталось добавить пустые разрешённые дни. Следующий шаг — добавить в тест контракта пример с двумя датами и пустым dishes у одной. Серверные запросы не выполнялись.

### 13.4. Препятствие

1. Записать причину и необходимое решение.
2. Указать ответственного и зависимые задачи.
3. Предложить пользователю готовую независимую задачу или действие для снятия препятствия и остановиться.
4. После нового указания пользователя сверить предположения и продолжить только согласованную подзадачу.

Ожидание магазина не блокирует расчёты. Отсутствие денежного контракта блокирует завершение корзины.

## 14. Порядок движения и ближайшие действия

**Подготовка → каркас → расчёты и сервер → авторизация → меню → корзина и заказы → сайт/PWA → приёмка и публикации → переход и стабилизация.**

Независимые работы можно предлагать к выполнению раньше: аккаунты, ключи и macOS — с подготовки; тексты — во время бизнес-функций; сервер — после контракта; инструкция миграции — до завершения UI; iOS-проверки — с каркаса. Переход к каждой следующей подзадаче требует нового подтверждения пользователя.

Начальная последовательность:

1. FL-00-01: документы и учёт.
2. FL-00-02: исходное состояние.
3. FL-00-03–04: матрица и NewProject.
4. FL-00-05–12: API и бизнес-правила.
5. FL-00-15: противоречия и решения.
6. FL-00-14: условия интеграционных проверок.
7. FL-00-16–17: оценка и приёмка подготовки.
8. Каркас и расчётная спецификация.

Ориентир ТЗ 9–12 недель сохранён как исходная оценка. После аудита рабочая оценка остатка, ресурсные предположения, серверные предшественники и внешние ожидания приведены в [FL-00-16](docs/tasks/FL-00-16.md). Версия 2.2 добавляет эту оценку без смены ID и состава задач. Оценка не является обещанной датой завершения. Документальное заключение о подготовке — [FL-00-17](docs/tasks/FL-00-17.md); оно не заменяет разрешение разработки или приёмку сборок из этапа 0 исходного ТЗ. Browser CORS FL-00-14d временно отложен пользователем и остаётся условием живой Web-приёмки.

Начальное состояние всех реализационных задач — «не начата». Завершение документальных задач отражается в карточках и не означает готовность приложения. Актуальный следующий шаг всегда указан в PROJECT_STATE.md.
